## 2026-07-18 - Implementer blocker: inaccessible Protobuf codec

- Before adding the first CRUD RED test, the implementer inspected the accepted
  adapter scaffold and the existing `RecordStorage` / `RecordSpec` port.
- `RecordSpec` retains its `GenMessage<R>` schema in the runtime-private
  `#record` field. Its public API only provides clone, ID extraction, and
  materialization; it does not expose a binary encode/decode operation or the
  record schema. `RecordStorage` supplies only materialized records to adapter
  hooks.
- The accepted T-0046 contract requires the adapter to persist a canonical
  Protobuf binary payload and deserialize fetched entities. With the current
  protected public storage contract, an adapter cannot call Buf `toBinary()` or
  `fromBinary()` for an arbitrary `R`; Protobuf messages do not carry their
  schema as a public value.
- This is a concrete blocker, not a design choice: implementing persistence
  now would require either changing `@spine-ts/storage` to expose a codec,
  using a non-Protobuf/invented payload format, or violating runtime privacy.
  The latter two conflict with the accepted plan and the implementer boundary.
- No production or test behavior was changed after the existing green factory
  port test. Await a plan/contract correction that makes the codec available
  without widening the generic public API, or explicit authority to amend that
  API.
- Focused revalidation after documenting the blocker passed:
  `pnpm --config.verify-deps-before-run=false exec vitest run
packages/storage-datastore/test/datastore-storage-factory.test.ts` (1 file,
  1 test) and `pnpm --config.verify-deps-before-run=false exec tsc --build
