  - `QueryService` is a thin type-router and delegates execution to
    `context.stand().execute(query, observer)`.
  - `Stand` validates target support and request format, then chooses an entity
    query processor.
  - Query validation rejects `limit` without ordering.
  - Query conversion maps ID filters, simple/composite filters, field masks,
    ordering, and limits to a storage `RecordQuery`.
  - The Java high-level `QueryBuilder` keeps a single ordering directive even
    though the proto allows repeated `order_by`; storage conversion can still
    process repeated proto orderings.
  - Column filters use top-level field paths; nested entity columns are rejected
    in JVM query construction/validation.

  - `validateReadQuery()` currently rejects column filters, masks, ordering,

    version metadata.

## Decisions

- Implement the first T-0017b slice by adding a small `Stand.queryVersioned()`
  path over storage `RecordQuery` and by converting supported query proto
  criteria/format in `SpineServices`.
- Keep support intentionally narrow and explicit: ID filters, top-level exact
  field filters, field masks, ordering, and positive limits. Reject unsupported
  composite operators or non-equality filter operators with deterministic
  `INVALID_QUERY` responses.
- Preserve JVM behavior that `limit` requires at least one ordering directive.
- Do not introduce a public query-builder API in this task; this task closes the
  server/read-side execution gap first.
- Use `RecordStorage.queryEntries()` for Stand query execution so version
  metadata remains keyed by the storage slot ID even when a response field mask
  omits the entity ID field.
- Preserve Protobuf-ES `$typeName` when applying storage masks; deleting it
  makes masked generated messages unsafe to clone or pack.
