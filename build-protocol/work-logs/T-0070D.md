### Provider evidence and constraints

- The installed official `@google-cloud/datastore` 10.1.1 declarations expose
  `Datastore.transaction()`, transactional `get`/`save`/`insert`/`delete`,
  transactional ancestor queries, `Query.hasAncestor()`, `Query.select()`,
  key filters through `__key__`, cursors, and `wrapNumbers`.
- Google documents transactions as atomic and serializable, warns that a
  reported commit failure may follow a successful commit, and identifies
  `ABORTED` contention as retryable. The adapter must therefore make every
  transaction idempotent and retry only bounded contention failures:
  <https://cloud.google.com/datastore/docs/concepts/transactions>.
- The compatibility floor remains the legacy entity-group mode: at most 25
  entity groups per transaction, transactional queries must be ancestor
  queries, and one entity group can be a contention/throughput hot spot.
  Current Datastore-mode transactions are limited to 10 MiB:
  <https://cloud.google.com/datastore/docs/concepts/limits>.
- Ancestor queries and point lookups are the provider's strong-consistency
  mechanisms. Keys-only projections are cheaper than full-entity queries:
  <https://cloud.google.com/datastore/docs/concepts/structuring_for_strong_consistency>
  and
  <https://cloud.google.com/datastore/docs/samples/datastore-keys-only-query>.
- Built-in indexes cover ancestor/key filters and ordinary ascending key
  scans. Multiple property orders require deployable composite indexes; a
  missing index fails the query. Fixed kinds are therefore mandatory:
  <https://cloud.google.com/datastore/docs/concepts/indexes>.
- Adapter constants are fixed and private: history read page size `128`,
  maintenance transaction chunk `8`, transaction attempts `3`, and the
  existing bounded exponential-jitter policy for gRPC code `10` (`ABORTED`).
  Eight rows keep worst-case event maintenance at or below 24 entity groups
  (entity root, immutable event row, and retention marker per selected event).

- Resolve the current tenant and validate the full input before the first RPC.
  Derive one canonical scope string byte-for-byte like the shared authority:
  length-delimited UTF-8 segments for context name,
  `single-tenant` or `tenant:<tenantId>`, and `storageKey`, joined with the
  shared separators.
- The shared provider SPI does not export `canonicalStorageScope`, and T-0070D
  does not own or reopen that frozen package. Use one adapter-private
  `datastoreScope()` implementation, consume its single result for binding,
  every key, and every range, and prove byte identity with the shared golden
  single-tenant, multitenant, UTF-8, and delimiter-collision vectors. Do not
  introduce a second encoding in the factory or fake.
- Encode arbitrary canonical strings in key names as lower-case UTF-8 hex.
  Encode signed 64-bit values as fixed-width 16-digit hex after adding
  `2^63`; use the complemented value when descending numeric order must become
  ascending key order. Encode timestamps as signed-seconds order plus validated
  nanos. Encode descending arbitrary UTF-8 bytes as complemented hex plus a
  terminator that sorts after every hex digit, preserving prefix ordering.
- Validate every completed Datastore key against the documented 6 KiB key
  bound and every indexed string against the 1,500-byte bound before a
  transaction, binding lookup, query, or row lookup. Oversize provider keys are
  rejected locally; no hashing may silently weaken collision-free identity.

  version descending, then canonical state-row-key bytes descending.

### Transaction algorithms

Use one private transaction runner: `run`, execute, `commit`; rollback on every
uncommitted exit; retry gRPC code `10` at most three times with the existing
bounded jitter. Do not retry validation, incompatible binding, divergent
content, malformed durable data, closed-handle, or generic provider failures.
Every transaction below is safe if the server committed but the client saw an
error.

1. **Durable first binding**
   - Locally validate input, canonical scope, fingerprint, namespace, and key.
   - In one transaction, get `$SpineEntityScope`. If absent, `insert` the exact
     scope/fingerprint row. If present, compare both exact values.
   - Concurrent incompatible first opens conflict at commit; the loser retries,
     observes the winner, and rejects before any current/history key is read.
   - Cache only a successful binding per handle. A transient failure clears the
     local promise so a later operation can retry. Local caching is an
     optimization, never a concurrency authority.

2. **Current record**
   - `write` validates the signed-64 version and serializes payload/ID before
     binding or any RPC, then performs the existing independent current-row
     save. `read` binds first and point-looks up the child row.
   - Current and history remain deliberately non-atomic across the frozen SPI;
     T-0070/T-0071 partial-failure semantics are unchanged.

3. **State append/retry**
   - Validate version, timestamp seconds/nanos, keys, order tokens, and payload
     before binding.
   - One transaction reads the entity root and state identity row. Create and
     validate the exact root on first use. If the identity exists, compare
     entity ID, original timestamp, version, and canonical payload: identical
     is a no-op; divergent rejects.
   - If absent, insert the state identity, state-order marker, and state-cut
     marker; increment root `stateCount` and revision. The root and descendants
     form one entity group; the cut marker is the second group.
   - All same-entity append/trim chunks read and update the root revision, so
     independent clients/processes conflict and retry through Datastore rather
     than a `WeakMap`.

4. **Event append/retry**
   - Validate event ID, producer version, timestamp, keys/order tokens, and
     payload before binding.
   - One transaction reads the global event identity and exact entity root. An
     existing identity compares event bytes, event ID, canonical entity
     correlation, producer version, and original timestamp. Identical is a
     no-op; any difference rejects.
   - If absent, insert the immutable identity, per-entity order marker, and
     global cut marker, and update the entity-root revision. This touches at
     most three entity groups and makes the event ID globally immutable within
     the canonical scope.

5. **State trim**
   - Each transaction reads the entity root. If `stateCount <= keepMostRecent`,
     it commits no mutation and returns complete.
   - Otherwise a kindless, ancestor, ascending-key, keys-only query selects at
     most `min(8, stateCount - keepMostRecent)` oldest
     `$SpineEntityStateOrder` markers. Parse version/time from each marker,
     delete its state identity/order/cut keys, decrement `stateCount`, and bump
     root revision atomically.
   - After every committed chunk, start a new transaction and restart selection
     from the oldest key. Never carry a retained/skipped counter or provider
     cursor across deletion. Persisted `stateCount` makes 129 rows with
     `keepMostRecent = 1` delete 8-at-a-time and stop with exactly one row.
   - A concurrent append is serialized against each chunk by the shared root.
     Whichever commits first is reflected by `stateCount` and the next
     selection; an appended row is deleted only if its version is genuinely
     outside the highest retained versions.

6. **State/event truncate**
   - Fix the caller boundary once. Before deleting, run one bounded descending
     keys-only query in the fixed cut kind/range with `limit(1)` and capture
     the highest eligible cut key. If absent, return.
   - Select at most eight cut keys in ascending stable key order between the
     scope lower bound and captured high-water key. The cut key contains every
     authoritative/order key input, so no payload row is read for selection.
   - Delete each selected state identity/order/cut triple or event
     identity/order/cut triple transactionally. State transactions also
     decrement each entity root count; both paths read/update the relevant
     entity revisions. Event chunks of eight touch no more than 24 entity
     groups.
   - Advance by the last stable cut key; do not use a cursor over deleted rows.
     On a later invocation, start again from the caller's fixed boundary.
     Completed chunks remain durable and missing selected keys are an
     idempotent no-op after exact root/count reconciliation.
   - A concurrent eligible append whose cut key sorts after the captured
     high-water survives for a later invocation. Earlier concurrent keys may or
     may not be observed, matching the frozen contract; no invocation chases an
     ever-growing live tail.

### Read bounds, lifecycle, and failure semantics

- `backward` validates positive safe `depth` and optional signed-64 exclusive
  version before binding. Query only the entity ancestor and relevant fixed
  order marker, with each provider limit `min(128, remainingDepth)`. Stop as
  soon as `depth` identities have been selected; do not inspect or fetch later
  pages. Batch lookups never exceed 128 keys.
- `stateAt` validates the boundary before binding and performs exactly one
  `$spineStateAt` ancestor query with `limit(1)`, followed by at most one point
  lookup of the authoritative state. It never scans past a found answer.
- Every operation validates all supplied/current-row versions, producer
  versions, continuation versions, timestamp seconds, timestamp nanos, finite
  query limits, encoded property sizes, and key sizes before the binding
  transaction or any other RPC. Timestamp nanos must be an integer in
  `0..999_999_999`; every indexed bigint remains exact signed 64-bit.
- Replace the client/scope `WeakMap<OperationGate>` with one local
  `HandleState` per `DatastoreEntityStorage`. Closing a handle rejects new and
  queued handle work but does not close the injected client, binding, entity
  root, factory, or sibling handles.
- An already-started transaction/chunk may settle. Maintenance checks the local
  handle after every settled chunk and starts no later chunk when closed.
  Ordinary active single-RPC/transaction operations settle normally. All
  subsequent operations use the standard `Entity history storage is closed.`
  error.
- Binding, append, and maintenance transaction commits are atomic. A failure
  after an earlier maintenance chunk leaves that chunk durable; retry resumes
  from durable keys/count/high-water selection. No claim is made that current
  and history writes, separate history calls, or later repository flushes are
  atomic together.
