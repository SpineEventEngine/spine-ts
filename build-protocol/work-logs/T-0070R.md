## 2026-07-24 — Accepted same-entity transaction design

### Classification and fixed boundary

- This correction remains high-risk because it changes durable concurrency,
  transaction, retry, and pool-lifecycle behavior. The existing
  `requirements_splitter` was explicitly dispatched as `gpt-5.6-sol` / `high`.
  This surface does not expose actual runtime model or reasoning
  self-introspection; the immutable explicit assignment profile is the
  available metadata.
- The frozen SPI, row identities, ordering, 128-row maintenance bound, public
  exports, and repository behavior do not change. The correction is MySQL-only
  and introduces neither a generic SQL abstraction nor PostgreSQL behavior.
- The current implementation is not sufficient: state append has no
  transaction and reads a duplicate on a second connection, while trim selects
  before beginning its transaction. An in-process queue would also fail across
  independent factories and processes.

### MySQL lock and connection ownership

- Use one MySQL user-level lock for each canonical
  `(database, scope_key, entity_key)`. Derive a database-specific name no longer than MySQL's
  64-character limit by SHA-256 hashing one unambiguous canonical tuple and
  prefixing it with a short adapter-owned state-history namespace.
- Acquire the exclusive lock with `GET_LOCK` on one admitted
  `PoolConnection`, passing `@@SESSION.innodb_lock_wait_timeout` as the bounded
  wait. Result `0`, `NULL`, or a provider error is an operation failure. Check
  the history handle again immediately after acquisition so close while
  waiting cannot start a mutation.
- Hold that one user lock and connection for the complete append or trim
  invocation. MySQL user locks survive transaction commit/rollback, so trim
  may commit bounded chunks without allowing a same-entity append between
  chunks. Release exactly once with `RELEASE_LOCK` before returning the
  connection to the pool.
- No lock table or migration is added. A permanent row lock would end at each
  chunk commit; keeping one row transaction open across all chunks would
  violate durable per-chunk resumability and close-after-active-chunk behavior.
- Replace the cast-and-monkey-patched entity `Pool` facade with a small
  entity-connection lease: the factory admits before `pool.getConnection()`,
  and the lease releases the lifecycle exactly once on either normal
  `connection.release()` or poisoned `connection.destroy()`. This is a
  lifecycle seam, not a provider-neutral SQL API.
- `createEntityStorage` must reject after factory close. Factory close marks
  handles closed, rejects new acquisitions, waits for an already admitted lock
  waiter/transaction to release or destroy its connection, and calls
  `pool.end()` only after that drain.

MySQL 8.4 documents that `GET_LOCK` is exclusive and server-wide, survives
commit/rollback, is released explicitly or when its session terminates, can
report `ER_USER_LOCK_DEADLOCK`, and limits names to 64 characters:
<https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html>. The
database-specific hash prevents unrelated adapter databases on one server from
sharing a name. This task supports the tested single-MySQL-server topology; it
does not claim cross-`mysqld` or NDB locking, and it must not claim
statement-based replication support for this user-lock path.

### Transaction algorithms

1. **State append:** validate and ensure schema/fingerprint readiness before
   protected mutation; acquire one lease and the entity user lock; begin one
   transaction; insert the immutable row. On `ER_DUP_ENTRY` only, select the
   existing row `FOR UPDATE` on the same connection and compare timestamp plus
   canonical payload. Commit an identical retry as a no-op; reject divergent
   content. Other insert errors do not enter retry comparison. Commit, release
   the user lock, then release the lease.
2. **State trim:** validate `keepMostRecent`, ensure readiness, acquire one
   lease and the entity user lock, and loop on that connection. For each
   iteration, recheck open, begin a transaction, select at most 128 deletion
   keys after the retained newest prefix using the frozen stable order and
   `FOR UPDATE`, delete exactly those selected keys, and commit. An empty
   selection commits/ends the operation. Recheck open only after the committed
   chunk, so close lets that bounded chunk settle but prevents another.
3. **Failure cleanup:** an uncommitted chunk rolls back best-effort. A prior
   committed trim chunk remains durable and a caller retry recomputes the next
   bounded selection. A commit error has unknown outcome and is not retried
   internally; append identity and trim deletion make a later caller retry
   safe. Provider deadlock/timeout/connection errors are sanitized as the
   existing MySQL operation error; validation, closed-storage, incompatibility,
   and deterministic divergent-retry errors retain their specific meaning.
4. **Lock cleanup:** `RELEASE_LOCK` must return success. If release fails or
   reports that this session does not own the lock, destroy rather than pool
   the connection so session termination clears any possibly retained user
   lock, and release the lifecycle lease once. No automatic SQL retry or
   configurable public lock policy is added.

State/event reads, current-record operations, event append, and both truncate
paths do not take this lock. The frozen cross-factory serialization rule is
specifically state append versus state trim for one entity; truncate retains
its separate fixed-boundary, resumable contract.
