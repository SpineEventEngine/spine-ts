## 2026-07-15 - Research Evidence

- Confirmed official ZeroMQ documentation says messages contain one or more
  frames, are delivered all-or-none, must fit in memory, and multipart framing
  does not reduce memory consumption.
- Confirmed ZMTP 3.1 defines the `MORE` bit per frame and requires atomic
  delivery of all frames in a message. Its normal socket semantics retain all
  frames until a complete message can be delivered.
- Confirmed libzmq's public `ZMQ_MAXMSGSIZE` option describes a byte limit for
  an inbound message part, and its v2 decoder checks each decoded frame size
  independently while tracking `MORE` as a separate flag. There is no aggregate
  multipart byte or frame-count option in the inspected socket-option surface.
- Confirmed zeromq.js 6.5.0 documents `receive()` as `Promise<Buffer[]>`. Its
  native `Socket::Receive` loop calls `zmq_msg_recv`, converts each part to a
  Node buffer, and continues while `zmq_msg_more` is nonzero before resolving
  the JavaScript promise.
- Found upstream zeromq.js issue 221 discussion that explicitly describes the
  whole-message behavior: the callback runs only after all frames are
  available, and unused later callback arguments are still passed/discarded.
  Found libzmq issue 2269 discussion of the receive-side atomicity guarantee.
- Ran bounded public GitHub issue searches over zeromq.js and libzmq using
  `maxMessageSize`, `MAXMSGSIZE`, `multipart`, `allocation`, `memory`,
  `frames limit`, `message parts limit`, `RCVMORE`, and denial-of-service terms.
  The search found related multipart/atomicity and memory issues but no issue
  or proposal dedicated to an aggregate multipart frame-count/byte cap or the
  exact zeromq.js pre-materialization gap.
- Research conclusion is necessarily calibrated: the underlying behavior is
  known and documented, while the exact missing aggregate guard appears not to
  have a dedicated public upstream report in the searched sources. Search
  absence cannot prove that Spine TS was first.
