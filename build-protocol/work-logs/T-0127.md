## Current official-source checks

- [Google managed instance groups](https://docs.cloud.google.com/compute/docs/instance-groups)
  confirm that MIGs provide autohealing, autoscaling, rolling updates, and
  load-balancer attachment.
- [Google rolling updates](https://docs.cloud.google.com/compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups)
  confirms proactive updates, surge/unavailable controls, stability checks,
  and rollback by applying the earlier instance template.
- [Google autohealing](https://docs.cloud.google.com/compute/docs/instance-groups/autohealing-instances-in-migs)
  confirms application health checks, configurable startup delay, and MIG
  stability/health inspection.
- [Google autoscaling](https://docs.cloud.google.com/compute/docs/autoscaler)
  confirms CPU, load-balancing, and per-instance metrics cannot scale to zero;
  a whole-group Monitoring metric can when minimum capacity is zero.
- [Google Monitoring metric scaling](https://docs.cloud.google.com/compute/docs/autoscaler/scaling-cloud-monitoring-metrics)
  distinguishes whole-group work metrics from metrics emitted by each VM.
- [Terraform regional MIG](https://registry.terraform.io/providers/hashicorp/google/latest/docs/resources/compute_region_instance_group_manager.html)
  warns that `target_size` fights an autoscaler and exposes update/autohealing
  configuration.
- [Terraform regional autoscaler](https://registry.terraform.io/providers/hashicorp/google/latest/docs/resources/compute_region_autoscaler)
  exposes explicit min/max capacity, CPU, whole-group metrics, filters, and
  single-instance assignment.
- [Terraform instance template](https://registry.terraform.io/providers/hashicorp/google/latest/docs/resources/compute_instance_template)
  recommends immutable replacement with `create_before_destroy` and a dedicated
  least-privilege service account.
- Google currently deprecates the Compute Engine container startup agent and
  `gce-container-declaration` metadata path. The template therefore uses
  Compute-Optimized OS and an explicit `docker run` startup script instead.
- Google documents regional internal passthrough load balancers with a reserved
  internal address, regional backend service, forwarding rule, health check,
  and managed-instance-group backend. The template uses this pattern for stable
  private Gateway and delivery addresses; group instances do not claim those
  addresses themselves. Sources:
  [overview](https://docs.cloud.google.com/load-balancing/docs/internal) and
  [MIG backend setup](https://docs.cloud.google.com/load-balancing/docs/internal/setting-up-internal).
- Internal passthrough load-balancer utilization is not a usable autoscaling
  signal. The template offers CPU or Cloud Monitoring whole-group/per-instance
  choices only, and documents that only an operator-provided whole-group metric
  can wake a zero-instance group.
