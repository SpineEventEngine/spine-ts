- `2026-07-08`: Read the local JVM docs on routing/dispatch/delivery,

- `2026-07-08`: Read focused `core-jvm/server` sources from
  `/Users/armiol/development/Spine/core-jvm/server/src/main/java/io/spine/server`:
  `projection/ProjectionRepository.java`, `projection/CatchUpEndpoint.java`,
  `delivery/CatchUpProcess.java`, `delivery/CatchUpStation.java`,
  `event/store/DefaultEventStore.java`, and `stand/Stand.java`.
- JVM projection catch-up is repository-owned and projection-specific. A
  `ProjectionRepository` exposes `catchUp(since, ids)` and `catchUpAll(since)`,
  starts a `CatchUpProcess`, and obtains historical events from the Bounded
  Context event store.
- JVM catch-up clears target projection records before replay. The
  `CatchUpEndpoint` handles `CatchUpStarted` by deleting the projection record
  and marking lifecycle readiness; it does not emit ordinary lifecycle events
  during catch-up.
- Historical replay is distinct from appending. `DefaultEventStore.read(...)`
  streams already stored events in chronological order; `EventBus.post(...)`
  stores before dispatch, but catch-up reads stored events and sends them to
  catching-up targets instead of re-appending.
- Full JVM Delivery catch-up is broader than this slice: catch-up jobs, inbox
  labels/statuses, shard coordination, turbulence/finalization, and maintenance
  stations coordinate historical and live messages. T-0017a intentionally does
  not implement these delivery/scheduler pieces.
- TS implementation boundary chosen for this task: add a small first local
  read-side catch-up API that clears projection state in `Stand` and dispatches
  already-stored events through the existing projection subscriber execution
  path. Do not add a durable `CatchUpStorage`, scheduler, shard station, retry
  loop, or Delivery-shaped abstraction yet.
- `2026-07-08`: Chosen TS catch-up surface:
  `BoundedContext.catchUpReadSide(options?)` with short exported
  `ReadCatchUpOptions` / `ReadCatchUpResult` types. The method is
  framework-owned, clears registered projection state via `Stand.clear()`,
  reads already-stored events from `EventStore`, sorts replay by
  timestamp/producer/version/id, and dispatches only registered projection
  repository event handlers. It does not append, re-envelope, or invoke custom
  app-side event dispatchers during catch-up.
- `2026-07-08`: Chosen tenant boundary: multitenant catch-up requires
  `options.tenantId`; single-tenant catch-up rejects `tenantId`. Stand writes
  during replay continue to derive tenant scoping from event context or the
  tenant-scoped catch-up storage context.
