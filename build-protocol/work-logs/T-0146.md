## Findings

- Current JVM Datastore uses native namespaces for tenant isolation. Namespace
  is applied to every key, query, and transaction. Stored entities contain
  serialized bytes and declared columns only; kind identity excludes Bounded
  Context.
- JVM Datastore tenant discovery reads native `__namespace__` metadata and does
  not persist `TenantId` records.
- Current JVM JDBC 2.x has one data source and does not currently implement
  tenant routing. It still proves that table identity and schema exclude
  Bounded Context, `_scope`, and `_revision`.
- Historical JVM JDBC `origin/multitenancy-support` at `603a4706` implements
  tenant-to-`DataSourceWrapper` selection from an enumerable map. Together with
  the human direction, this freezes the TS target as one configured database
  or data source per tenant.
- Spine TS `_revision` is never read for CAS or conflict decisions. Exact CAS
  already relies on transactions/locks and serialized-record comparison.
- Spine TS `_scope` affects MySQL primary keys and predicates, Datastore keys
  and filters, in-memory identity, EventStore/cache identity, and lock names.
  All must be removed; no replacement discriminator is allowed.
- The server's direct `TenantId` record family is another invented persistence
  mechanism. Tenant startup enumeration must become a provider-owned
  capability: native Datastore namespaces, configured MySQL tenant databases,
  or in-memory tenant slices.

## JVM interoperability decision

- Human direction froze physical interoperability with Spine JVM as a required
  outcome, not an optional compatibility choice.
- JVM uses typed `RecordSpec`/`RecordColumn` metadata and provider
  `ColumnMapping` conversion symmetrically for stored values and query
  operands. `Identifier` handles supported ID forms and Any packing;
  `Stringifiers` provides reversible message text, with compact Proto JSON as
  the default message representation.
- Current TS differs materially: entity columns collapse to the free-form
  `"protobuf"` value type; MySQL message IDs use deterministic Proto binary;
  primitive MySQL IDs and Datastore keys use private tagged formats; message
  columns may use generic JavaScript JSON; and write/query paths do not share
  one schema-aware mapping.
- The plan now requires schema-aware column metadata, JVM-shaped identifier and
  stringifier contracts, provider mappings used identically by writes and
  queries, removal of TS-only encodings, and JVM/TS golden interoperability
  fixtures for all supported ID and column types.
- This clarification changes no production TypeScript, provider schema, or JVM
  source. It strengthens the non-releasable T-0147 through T-0150 acceptance
  unit before implementation starts.
