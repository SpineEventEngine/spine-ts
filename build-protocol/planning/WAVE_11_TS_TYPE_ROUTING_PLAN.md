# Wave 11: TypeScript Interfaces And Interface-Based Routing

Status: Specialist review corrections applied; targeted re-review pending

## Purpose

Wave 11 adopts the fresh upstream `ts_type` contract for `(is)` and
`(every_is)`. It teaches Spine's TypeScript generation step to produce or find
the declared interfaces, verifies that generated messages conform to them,
emits same-named runtime tokens, and lets existing routing declarations accept
those tokens through `.route(...)`.

The wave also corrects the generated-source policy: generated TypeScript says
that it is generated, identifies its stable Proto source, and never carries a
CodeMatters copyright header.

The canonical human requirements are recorded in
[`T-0178`](../tasks/T-0178-wave11-plan/TASK.md).
The accepted architecture decision is
[`D-0113`](../DECISION_LOG.md#d-0113-generate-typescript-message-interfaces-and-route-by-their-tokens).

## Approved User Model

### Proto declaration

The To-Do event file will declare one generated common interface:

```proto
option (every_is) = {
  generate: true
  ts_type: "TaskEvent"
};

message TaskAssigned {
  option (is).ts_type = "TaskAssignmentEvent";

  TaskId task = 1;
  TaskListId list = 2;
  spine.core.UserId assignee = 3;
}
```

`TaskEvent` is generated because the file option says `generate: true`.
`TaskAssignmentEvent` is authored in the application's ordinary TypeScript
source because `(is)` never generates an interface.

### Authored interface and inheritance

The authored interface may extend another interface from the same Proto model
module:

```ts
import type { UserId } from "@spine-event-engine/core";
import type { TaskId } from "../generated/spine/examples/todo/task_id_pb.js";
import type { TaskListId } from "../generated/spine/examples/todo/task_list_id_pb.js";
import type { TaskEvent } from "../generated/interfaces/task-event.js";

export interface TaskAssignmentEvent extends TaskEvent {
  readonly task?: TaskId;
  readonly list?: TaskListId;
  readonly assignee?: UserId;
}
```

Here, _model module_ means the application/package root described by
`spine-proto.json`, not one TypeScript file. The declared interface and every
interface in its `extends` chain must resolve inside that model module after
realpath normalization. Property types may come from dependencies, as `UserId`
does above. Re-exporting an external parent through a local barrel does not make
it local.

### Generated companion

The post-Buf phase emits a companion under `generated/interfaces/`. For an
authored interface, the companion imports the real authored declaration under a
private alias and re-exports that type. It does not declare a second, empty
interface. The same public export name works in both TypeScript namespaces:

```ts
import { TaskAssignedSchema, TaskUnassignedSchema } from "../spine/examples/todo/task_events_pb.js";
import { MessageInterfaces, type MessageInterface } from "@spine-event-engine/core";
import type { TaskAssignmentEvent as AuthoredTaskAssignmentEvent } from "../../src/task-assignment-event.js";

/** Generated by Spine TypeScript from spine/examples/todo/task_events.proto. */
export type TaskAssignmentEvent = AuthoredTaskAssignmentEvent;

const memberSchemas = [TaskAssignedSchema, TaskUnassignedSchema] as const;

/** Generated by Spine TypeScript from spine/examples/todo/task_events.proto. */
export const TaskAssignmentEvent: MessageInterface<
  AuthoredTaskAssignmentEvent,
  typeof memberSchemas
> = MessageInterfaces.define<AuthoredTaskAssignmentEvent, typeof memberSchemas>(memberSchemas);
```

The exact formatting may change during implementation, but the public naming
does not: `MessageInterface` is the immutable token type and
`MessageInterfaces.define()` is its supported low-level public factory.
Generated modules call the factory; most applications import generated tokens
instead. Because JavaScript cannot prove which source generator called a public
function, the contract does not claim token provenance authentication. The
factory validates, copies, deduplicates, and freezes its schema membership;
routing rejects copied plain objects and structurally incomplete tokens. A token
returned directly by the supported factory is valid, including when imported
from another model package.

Generated message aliases explicitly include every applicable generated or
resolved authored interface. The TypeScript compiler, using the model module's
own configuration, proves each concrete member satisfies that intersection and
types an interface route callback as the concrete member union intersected with
the interface.

The public type relationship is frozen as the following equivalent contract
(implementation details may use private helpers):

```ts
type InterfaceSchemas = readonly [MessageSchema, ...MessageSchema[]];
type InterfaceMember<Schemas extends InterfaceSchemas> = MessageShape<Schemas[number]>;

interface MessageInterface<TInterface extends object, Schemas extends InterfaceSchemas> {
  readonly schemas: Schemas;
  // A private unique-symbol brand prevents structural object literals/copies.
  // Its covariant witness also makes every member shape assignable to TInterface.
}

const MessageInterfaces: {
  define<TInterface extends object, const Schemas extends InterfaceSchemas>(
    schemas: InterfaceMember<Schemas> extends TInterface ? Schemas : never,
  ): MessageInterface<TInterface, Schemas>;
};
```

The conditional factory input is the generated compile-time witness that every
derived schema member implements `TInterface`. `TInterface` is object-shaped;
`Schemas` is statically constrained to the non-empty readonly tuple
`InterfaceSchemas`. Runtime construction also rejects dynamically malformed or
empty JavaScript inputs, duplicate schemas, and malformed entries, then copies
and freezes the tuple.

### Routing use

```ts
const routing = EventRouting.create<UserId>()
  .route(TaskReassignedSchema, (event) => [event.previousAssignee, event.newAssignee])
  .route(TaskAssignmentEvent, (event) => [event.assignee])
  .replaceDefault(() => []);
```

For a token `MessageInterface<TInterface, Schemas>`, each routing overload uses
this exact callback message type:

```ts
type InterfaceRouteMessage<
  TInterface extends object,
  Schemas extends InterfaceSchemas,
> = MessageShape<Schemas[number]> & TInterface;
```

Command routing returns one ID; Event and state-update routing retain their
existing zero-to-many result contracts. A callback may use only fields present
on the declared interface (or safely narrowed concrete members); compile-fail
fixtures reject non-schema membership, incompatible interface/member pairing,
and unconditional access to a field absent from one union member.

The overload is `.route(...)` for both schemas and generated interface tokens.
Wave 11 does not restore `routeSemantic()` and does not add `@Route`.

Resolution is:

1. an exact `MessageSchema` route;
2. the first matching interface-token route in explicit registration order;
3. the replacement/default route.

Exact routes win regardless of call position. When two interface tokens match,
the first registered token wins. Spine TS does not infer interface specificity
or reorder application declarations.

```mermaid
flowchart LR
    A["Accepted signal"] --> B{"Exact schema route?"}
    B -- Yes --> C["Run exact route once"]
    B -- No --> D{"First registered matching interface token?"}
    D -- Yes --> E["Run that token route once"]
    D -- No --> F["Run replacement/default route"]
    C --> G["Validate and persist typed Inbox target(s)"]
    E --> G
    F --> G
    G --> H["Replay stored targets without routing again"]
```

## Generation Pipeline

The semantic phase is part of model generation, not a separate manual command:

```mermaid
flowchart LR
    A["Authored Proto + authored TS"] --> B["Buf generates staged TS"]
    B --> C["Read frozen ts_type options"]
    C --> D["Emit provisional interfaces/tokens"]
    D --> E["Build one stable model-module TypeScript source view"]
    E --> F["Validate locality, inheritance, and assignability"]
    F --> G["Augment message types and finalize tokens"]
    G --> H["Rewrite imports and module exports"]
    H --> I["Atomically publish generated tree"]
```

Any diagnostic before the final step leaves the previously published generated
tree unchanged. Temporary directories, worktree roots, and absolute paths
never enter output.

The compiler source view reads authored source and `tsconfig` from the live
model module, excludes the configured `generatedRoot`, staging trees, backup
trees, declaration outputs, and symlink/realpath escapes from authored
interface candidates, and redirects generated imports to the staged Buf tree.
Generated files may participate in compiler conformance but never become
authored-interface candidates. The generator records content digests for every
authored/config input before analysis and verifies them again before publish;
concurrent source changes fail the run rather than validating one revision and
publishing another. A second generation therefore cannot rediscover its prior
companions.

## Generated-Source Contract

- Generated TypeScript has no copyright header and contains no `CodeMatters`
  notice.
- The file-level block says Spine TypeScript generated the file, warns not to
  edit it manually, and lists the stable source Proto import path or sorted
  source paths. A multi-source registry lists all of its stable sources; it does
  not use an untestable generic exception.
- Generated declarations name the stable Proto import path that produced them.
- A multi-source registry also gives each generated declaration its own source
  provenance.
- Buf output copied from a copyright-bearing Proto source is normalized before
  publication, so the source header does not leak into generated TypeScript.
- Generated outputs are excluded from authored-source copyright requirements.
  Enforcement rejects a CodeMatters header when one appears in a known
  generator-owned output.
- Authored TS/TSX/Proto retains the 2026 header and exactly one following blank
  line. Wave 11 does not weaken that rule.

## To-Do Domain Proof

The example remains a small, plausible task-management domain.

### Model changes

- Add a real `TaskListId`.
- `CreateTask` carries `TaskId`, `TaskListId`, and title.
- Task state retains its list and optional current assignee.
- Add `AssignTask`, `ReassignTask`, and `UnassignTask`.
- Add `TaskAssigned`, `TaskReassigned`, and `TaskUnassigned`.
- Every Task event carries enough list identity for `TaskList` routing.
- `TaskAssigned` and `TaskUnassigned` declare
  `(is).ts_type = "TaskAssignmentEvent"`.
- `TaskReassigned` has no `TaskReassignmentEvent`; its old/new-assignee fan-out
  is an exact-schema route.
- Commands carry no `(is)`/`(every_is)` marker in this example.

### Projection benefit

`TaskList`, keyed by `TaskListId`, registers one `TaskEvent` route instead of
one route per Task event. An assignee-oriented Projection, keyed by `UserId`,
registers one shared `TaskAssignmentEvent` route for assignment and
unassignment, plus one exact `TaskReassigned` route for two-target fan-out.

This demonstrates why an interface is useful: the repository expresses the
business grouping once, while each concrete event keeps its own schema and
handler.

The beginner journey must follow one task through the whole lifecycle:

1. `CreateTask` creates the task in its `TaskList` with no assignee target.
2. `TaskAssigned` follows the shared `TaskAssignmentEvent` route to one
   assignee Projection.
3. `TaskReassigned` follows its exact route to the old and new assignees,
   demonstrating exact-over-interface precedence and two targets.
4. `TaskUnassigned` follows the shared interface route to the former assignee;
   an explicit no-target case demonstrates zero-target Event routing.
5. A persisted Inbox row is replayed to show that none of these application
   routes runs a second time.

## Review And Verification Policy

Implementation uses one `gpt-5.6-terra` / medium writer at a time. Mechanical
verification uses `gpt-5.6-luna` / low or medium. Public contract,
compatibility, dispatch, build atomicity, and reliability reviews use the
existing Terra/high specialist roles. Documentation review uses the existing
Luna/medium role. Each task records explicit profile dispatch before the child
runs and records the runtime-metadata limitation when the surface does not
expose telemetry.

Every implementation task begins with behavior RED evidence and runs the cheap
preflight before its one selected expensive profile. `verify:release` is used
for shared generation, Proto, core, server, and final convergence. The isolated
To-Do and documentation tasks use bounded `verify:task` profiles unless their
actual diff expands into shared runtime/build behavior.

## Security Disposition

The plan introduces no new network, authentication, secret, or tenant boundary.
Generated-source path containment and compiler input confinement are
correctness and supply-chain concerns and receive fail-closed tests plus
reliability review. The existing final security reviewer runs in T-0186. An
earlier security lane is opened only if implementation changes a trust boundary
or accepts executable input outside the model module.

Wave 11 does not implement multiple Gateway instances, selection, failover,

provisional Gateway API. Multiple-Gateway work belongs wholly to Wave 12.
