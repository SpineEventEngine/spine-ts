# Per-handle storage preparation

High-risk prerequisite to persistent tenant/auth factories. Scope: common storage contract and built-in memory/MySQL/PostgreSQL/Datastore record handles. Preserve current business defaults.

## Requirements

The complete Human-Imposed Requirements Ledger in TASK.md applies. Add optional immutable per-handle preparation choice at the StorageFactory record-handle seam. Omitted/true preserves current preparation. Explicit false suppresses all schema existence/compatibility checks and structure creation during handle binding and data operations, without suppressing actual connection/data/CAS behavior. Unsupported custom factories reject before ignoring the option. Existing explicit StoragePreparations create/check remains usable.

## Acceptance

- Default handle still prepares lazily as today.
- False handle performs neither schema checks nor DDL for reads, writes, queries and conditional mutations. Missing structures fail normally.
- Same factory/context/spec/group handles can use different settings concurrently without mode or promise leakage.
- Another handle preparing the family does not change the false handle policy. Failed preparation and retry do not contaminate it.
- Handles close independently and injected factories remain available.
- Current explicit create/check behavior and all existing business paths remain unchanged.
- Domain-correct fixture messages, documented public option and provider implementation tests.

## Proposed seam

Optional fourth RecordStorageOptions argument with prepareOnAccess?: boolean. A protected no-preparation creation hook rejects by default in custom factories and is implemented by built-ins; existing default hook stays unchanged. PostgreSQL still binds destinations, MySQL skips both lifecycle and fallback preparation. No server/auth runtime edits in this slice.
