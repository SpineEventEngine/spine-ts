# Persistent signed-token revocations

High-risk authentication and persistence slice. The complete TASK human ledger,
PROPOSAL and accepted architecture govern implementation.

## Contract

PersistentTokenRevocations implements the existing SignedTokenRevocation port in
the auth package. Its private-constructor async factory accepts the selected
storage/group, issuer/audience scope and default-true preparation option. Its
record uses an unambiguous issuer/audience/token-ID identity and a retention
deadline. Insert or extend atomically; a concurrent shorter request cannot
weaken the deadline. Contains uses a primary-key read. Cleanup is explicit,
indexed and conditional, with cancellation and no scheduler/retention default.

Use the verified jose pin for standard signing/verification. Preserve existing
ES256, kid, claims, token-size, explicit lifetime/clock tolerance and retired-key
semantics. Revocation retention includes the full last acceptance window,
including configured clock tolerance. SignedSessions supplies that full deadline;
the store does not add tolerance again. The endpoint is inclusive, so cleanup
removes only deadlines strictly before the cutoff. A retained expired row no
longer revokes a token even before manual cleanup.

The existing clock rejects instants outside the Protobuf Timestamp range. If
expiry plus tolerance exceeds that range, retain through the maximum complete
Timestamp, including its final nanoseconds. This covers every representable
acceptance instant without changing the clock domain or adding a retention policy.
Use exact arithmetic and test the last valid millisecond; clamping to the maximum
whole second alone would shorten the window. Keys remain application configuration.
No persistent Session or user table is needed for this strategy.

## Acceptance

Bidirectional old/new golden-token checks establish preserved token semantics.
Test exact expiry/skew boundaries, retired and unknown keys, wrong algorithms,
issuer/audience isolation, concurrent retention extension, explicit cleanup,
preparation skip/default modes, failures and independent-instance persistence.
Test delayed revocation reads crossing expiry and the maximum Timestamp boundary,
including out-of-range clock rejection and the ordinary inclusive endpoint.
Expiry-only behavior without a revocation source remains explicit.
