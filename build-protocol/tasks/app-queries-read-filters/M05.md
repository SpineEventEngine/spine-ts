## Implementation and source guardrail

Inspected the pinned JVM `core-jvm-f2926a58` `BoundedContextBuilder.java`
handler-registration/assembly path before changing TS assembly. It selects
explicitly registered Entity and standalone classes. TS retains that explicit
selection; Java reflection does not justify a runtime package scan. The
generated bootstrap imports passive descriptions without constructing handler
instances or starting a Server. `registerSpineMetadata` validates descriptions
with the existing `HandlerRegistryIngestor`, indexes exact constructors, rejects
conflicting module descriptions, and reports missing bootstrap/class metadata
before assembly. BC `.add()` continues to select classes directly. The public
`withGeneratedRegistryRoot` option and its direct callers are removed; useful
explicit registry ingestion remains.

The existing Proto generation pipeline now stages both
`generated/spine-metadata.ts` and `generated/spine-bootstrap.ts`. The direct
`spine-proto handlers` helper also writes this pair and removes its retired
`generated/handler/generated-handler-registry.ts` file after successful output.
The helper stages both files and restores prior metadata if bootstrap
publication fails. Generated metadata imports local class declarations and the
ordinary Proto module; the bootstrap registers those descriptions with a
stable module label. Model/browser imports stay separate from Server runtime.
The six examples with entrypoint cycles now have separate declaration modules
and one static bootstrap import at the assembly entrypoint: Todo, Projects,
Orders (including cross-context and query-routing), Support, Message Board,
and Release Notes. Current README/REFERENCE/guide paths were migrated. M06
transitive dependency discovery and package `/spine` exports remain separate.
