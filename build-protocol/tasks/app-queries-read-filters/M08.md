# M08 — Trusted reader context and replaceable authentication ports

Status: prepared; implementation waits for M07 acceptance.
Classification: high-risk authentication, forwarding and subscription identity.
Expected implementer: existing app_query_implementation, explicit Sol/medium.
Estimate: 1.5–2.5 hours for ports, forwarding, isolation tests and review.

## Human-Imposed Requirements Ledger

TASK.md and PROPOSAL.md remain binding. ActorContext is not authenticated identity.
The application node receives verified principal and authority facts when present;
public access may have no principal. Filters and App Queries run after auth on
app nodes, never gateways. Auth/provider integration follows replaceable ports;
no provider polling or guarantee of live provider data. Never forward provider
credentials or treat the existing public-admission marker as a verified user.

## Existing boundary evidence

Read M08_BASELINE.md. The inspected current framework has session/auth/context
ports at the gateway, but no authenticated forwarding-peer channel and no
app-node direct-native authentication adapter in Server assembly. TLS server-name
configuration authenticates the remote server, not a forwarding client. The
approved trusted forwarding contract must therefore establish peer trust through
a configured replaceable port; copying headers from arbitrary callers is not
sufficient. No current trusted identity carrier should be invented in documentation.

## Scope

Extend the existing auth, request forwarding and Server assembly surfaces with
the smallest coherent ports for direct authentication and trusted forwarding.
Carry a detached, bounded internal execution context for Read, Execute and
subscription admission/activation. Resolve trusted actor/tenant separately from
principal/authority facts, preserving existing policy and context checks. Public
ingress must reject or strip caller-supplied copies of internal identity. Only
a configured authenticated forwarding peer can assert that internal context.
Do not silently trust loopback, a header name, a claimed ActorContext, or a Q field.

Keep provider facts independent of live credentials and allow application-defined
implementations to refresh facts according to their own policy. Default behavior
must clearly distinguish authenticated and public requests, with no process-wide
current-user field. Ensure native, browser, coordinator and managed-child paths
retain the verified context rather than rebuilding trust from the Proto request.
Bind retained subscriptions to the admitted reader and recheck the verified reader
on activation/reconnect/cancellation. Preserve existing actor/tenant isolation.
Use current transport limits to bound the serialized internal context.

## Acceptance and guardrails

Read current corresponding JVM service context/auth interception sections and
record which TS-specific port is required by the approved application-level design.
Tests cover authenticated gateway, direct native, public/no principal, forged
internal headers/ActorContext/Q claims, another principal using an existing
subscription ID, concurrent readers, reconnect and managed-child forwarding.
Prove provider credentials are absent from forwarded context and data remains
detached between invocations. Test replaceability, not a provider-specific poller.

If source evidence exposes an architectural ambiguity that cannot be resolved
within the approved port contract, present the concrete conflict to the main
orchestrator; do not invent a larger auth subsystem. Otherwise continue with the
smallest implementation. Focused auth/transport/client tests, changed coverage,
typecheck/build and cheap checks precede all relevant reviewer concerns. Dedicated
security review remains M14. Record evidence here, freeze for review, and do not
commit/push or begin M09 before acceptance.
