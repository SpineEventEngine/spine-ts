# M08 current-source baseline

Scanned at checkpoint `cc19b416d`. This is a source inventory for M08, not a security review or contract decision. The working tree has unrelated/concurrent M03/M05/M06 documentation and Proto-source changes; this scan does not claim those later edits are complete.

## Contract anchors

- M08 scope and acceptance are in `MILESTONES.md:277-300`; the task ledger requires trusted principal/authority to reach app-node execution through replaceable ports, rejects forged forwarded context, allows absent principal, and keeps public admission distinct from authentication (`TASK.md:44-54`).
- Proposal trust model is `PROPOSAL.md:393-416`. It explicitly says current forwarding lacks authenticated identity (`:406-408`), requires a package-internal envelope over the authenticated gateway-to-node path (`:410`), direct-native auth through a configured adapter and no credentials/public-marker promotion (`:412`), and verified reader binding through subscription activation/reconnect (`:414`).

## Existing facts and replaceable ports

- `packages/auth/src/index.ts:257-270`: `AuthenticatedPrincipal` is `{ id, attributes?: Readonly<Record<string,string>> }`. This is the current principal representation; no authority/provider-fact carrier appears in the public auth contracts inspected.
- `packages/auth/src/index.ts:316-350`: `ResolvedSession` carries principal plus expiration; `Authenticator` and `SessionResolver` are replaceable credential-validation boundaries. `packages/auth/src/index.ts:357-435`: authorization is an `AuthorizationPolicy`; `AuthorizedRequestContext`/`ContextResolver` resolve actor, optional tenant, timestamp, zone and language. These are trusted ActorContext facts, distinct from principal/provider facts.
- `packages/auth/src/gateway/index.ts:46-59` defines unary request facts (service/method/value/credential/transport/signal); `:83-98` defines the forwarding callback without credential or principal fields; `:100-135` has mutually exclusive session vs `publicAccess:true` admission. `UnaryGateway.handle` around `:280-329` decodes, resolves session, authorizes, independently resolves actor/tenant, rejects stale/fabricated actor/tenant, then forwards rewritten bytes only. Query rewriting is `:500-520`; forwarding currently carries value and signal, not the authenticated principal/context envelope.
- The public mode synthesizes `{ id: "spine-gateway-public" }` (`gateway/index.ts:363-377`; subscriptions `subscriptions/index.ts:979-1002,1339`). This is an admission sentinel used by current policy resolution, not verified provider identity. Browser assembly selects the public/session branch at `packages/server/src/browser/browser-server.ts:219-235`.

## Ingress and forwarding path

- Browser ingress: `packages/server/src/browser/browser-server.ts:405-440` builds credential extraction from cookie adapter or Bearer header and allowlisted transport facts. `:219-281` constructs `UnaryGateway`, `SubscriptionGateway`, and `createNativeGatewayServices`, with app-selected session/public mode, authorization, context resolution, and dynamic native forwarder. `packages/server/src/browser/options.ts:30-59,150-165` exposes those replaceable adapters.
- Native public RPC adapter: `packages/auth/src/native/index.ts:395-414` defines `NativeGatewayRequestContext` to extract credential and transport facts. `:482-621` routes ResolveContext/Post/Read through unary gateway; `:649-771` routes subscription operations through `SubscriptionGateway`. It currently passes the extracted credential into gateway admission and never directly forwards it to app services. `:528-547` strips downstream transport status headers when converting public errors.
- Direct/native app-node ingress is not the same path as browser gateway composition. The native service handlers are configured by `createNativeGatewayServices` (`native/index.ts:482-514`); server composition/configuration should be traced during implementation to identify the configured direct-auth adapter. The browser server is a gateway host that forwards to native application nodes, while its direct native connector is a transport component (`browser-server.ts:181-209`).
- Coordinator unary forwarding: `packages/server/src/server/node-coordinator.ts:425-440` snapshots Query/Command plus `HandlerContext`; `:664-670` types those request variants. `:885-910` calls native Query/Command using `applicationHeaders`, timeout and signal, and receives response metadata. `:970+` filters/copies application headers. The current internal forwarding request has no separate verified identity envelope. Subscription child activation/cancel crosses native transport at `:859-872,924-935`; hooks can observe child lifecycle but do not currently carry principal facts.
- Managed child hook is deliberately ID-only: `packages/server/src/server/managed-child-subscription.ts:14-45` reports installation once per child ID. It is a replaceable coordination seam, but does not itself retain a reader principal.

## Subscription context and serialization boundaries

- `packages/auth/src/subscriptions/index.ts:888-910` constructs the gateway with replaceable bindings, authorization, context resolver, clock, coordinator and admission mode.
- Admission/security currently resolves the session separately for every operation (`:979-1002`), resolves trusted ActorContext (`:1005-1035`), checks requested actor/tenant identity, and rewrites Topic/Subscription ActorContext (`:1045-1065,1410-1477`). The session principal is not included in `PreparedOperation`/forwarded topic as currently represented.
- `:1071-1145` rechecks activation via binding ID/context and `:1149-1218` coalesces/carries cancellation by actor/tenant ActorContext. `:1194-1220` creates a binding using rewritten Topic and expiration. Thus current reader binding is actor/tenant-context based; principal/provider facts are not retained in this gateway execution path.
- Durable boundary: `packages/server/src/browser/durable-subscription-bindings.ts:162-195` persists `GatewayAuthenticatedSubscription` with ID and cloned Subscription (which contains Topic/ActorContext); `:212-271` checks the current supplied ActorContext on activation/cancel. Proto storage serialization does not currently include a separate verified principal/provider envelope.
- Wire boundaries are Protobuf `toBinary/fromBinary` for Query/Topic/Subscription and response objects (native service conversion and subscription helpers); coordinator carries RPC messages and allowlisted Headers over Connect transport. The proposal requires principal/context metadata be internal and bounded, not placed in Q or ActorContext (`PROPOSAL.md:406-416`).

## Follow-through: internal peer authentication and direct-native adapter

At this checkpoint, source inspection found **no authenticated gateway-to-app-node peer channel or peer-authentication interceptor** in the inspected assembly. The existing `SessionResolver` authenticates an end-user credential at the browser gateway; the resulting principal currently stops at `UnaryGateway` authorization because its `UnaryForwarder` contract contains service/method/value/signal only (`packages/auth/src/gateway/index.ts:83-98,280-329`). Browser forwarding builds an HTTP/2 transport with `baseUrl`, optional `sessionManager`, and optional TLS `servername` (`packages/server/src/browser/browser-server.ts:181-199,495-505`); no client certificate, peer token, or authenticated transport identity is configured there.

The distinction at the TLS seam is explicit in `packages/deployment/src/discovery/application-node.ts:36-78`: `tlsServerName` is accepted only for `https:` endpoints and normalized as a server name. Browser transport passes it as `nodeOptions.servername` (`browser-server.ts:501-505`), which configures TLS server-name validation/SNI; the inspected APIs provide no client-authentication material or peer principal. The coordinator's managed-child listener instead uses `http2.createServer` (`packages/server/src/server/node-coordinator.ts:320-343`), and managed member clients use `Http2SessionManager(member.endpoint)`/`createGrpcTransport` without auth metadata (`:842-852`). This is transport topology and (for HTTPS) server authentication evidence, not proof of the gateway's identity at the app node.

App-node RPC registration also does not expose a direct-native auth adapter in the current API: `packages/server/src/server/server.ts:978-1009` creates an HTTP/2 listener with `connectNodeAdapter` and routes registered `SpineServices`; `packages/server/src/services/spine-services.ts:245-269` registers Query/Command/Subscription handlers without passing `HandlerContext` into those service methods. Separately, `packages/server/src/browser/browser-server.ts:281-288` wraps its browser-facing listener with `createNativeGatewayServices`, whose `NativeGatewayRequestContext` is an adapter for extracting user credentials/transport facts from the incoming Connect context (`packages/auth/src/native/index.ts:395-414`). That adapter is configured only in this browser gateway composition (`browser-server.ts:405-440`); it is not an app-node/direct-native auth hook.

Consequently, the current source contains replaceable user-session, policy, trusted ActorContext, and browser credential-extraction ports, but no existing port that supplies an authenticated internal peer identity or verified principal/provider facts to app-node Query execution. No source evidence found that TLS server-name selection or the coordinator's loopback endpoint establishes peer authentication. This records the present call graph only; it does not prescribe the M08 implementation.
