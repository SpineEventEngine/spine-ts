## Controlled SQL retry fault design

For first/second deadlock-class failures, prefer task-local SQL triggers returning the driver's genuine deadlock code, and label them injected errors rather than claiming an engine discovered a real lock cycle. PostgreSQL can use a task-local sequence to count attempts because nextval is not rolled back with the failed statement, then raise SQLSTATE40P01 for the selected attempts. On MySQL/MariaDB an ordinary transactional counter update inside a failing trigger rolls back, so it cannot implement a finite failure budget. A dedicated nontransactional test-only counter table or another supported deterministic control is required; use only the fresh run database and drop every trigger/function/counter afterward. SIGNAL SQLSTATE40001 with MYSQL_ERRNO1213 models the driver's deadlock-class failure. Validate each server's returned code and counter before claiming a retry count. These are disposable fault controls, not framework persistence or runtime patches. No live outcome is claimed here.

Fault-control mechanics verified on all four task servers: evidence/sql-fault-controls.mjs and sql-fault-controls-live.log.
