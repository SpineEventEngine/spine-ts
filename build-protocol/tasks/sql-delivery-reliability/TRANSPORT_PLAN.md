## Smallest implementation additions

Add one opt-in infrastructure integration file for the SQL-backed Project subscription lifecycle, plus a small test-only transport/server fixture module if needed. Register the new file in `scripts/test-inventory.mjs`; select it through the infrastructure Vitest config. Reuse the actual four endpoints documented in `SETUP.md` and the existing storage factory setup used by the live PostgreSQL/MySQL integration suites. Each test case must create unique SQL database namespaces/tenant IDs where the provider API supports them and clean them in `finally`. Avoid coupling the four-engine parameterization to provider-specific behavior beyond the existing storage factories.

Use one common Project handler topology, parameterized by Delivery mode (local/database-only vs shared Delivery), and protocol:

- Native: use the managed server's actual gRPC listener and `Client.connectTo`.
- Browser gRPC-Web and Connect: start the actual `BrowserServer` over the test's native service endpoint and use `Client.forGrpcWeb` / `Client.forConnect`. Existing BrowserServer integration proves these HTTP/1.1 paths work. Pass valid test origin/session/admission settings from the server fixture.
- BrowserServer exposes the supported test seam `BrowserServerOptions.bindings` (`packages/server/src/browser/options.ts`); decorate a real `SubscriptionBindings` implementation in the test fixture to pause/count `activate` and `cancel`, delegating to the real binding after each gate. That is suitable for deterministic browser gateway ACK and resource lifecycle tests. Do not monkeypatch production prototypes.
- The native listener does not use BrowserServer's bindings seam. For native ACK/cancel gates, compose a test-only Connect router/adapter around the real SubscriptionService implementation, or use an existing supported server listener seam if one is added by the implementation agent. The fixture must still invoke the real subscription service and SQL-backed handlers. Do not claim native gating from BrowserServer binding tests.
- Count server-side activation/cancel calls and active registrations in the fixture. Observe managed process IDs through the existing child-process harness where process topology is under test. Observe SQL state using existing provider query surfaces. No production-only hooks are needed for the browser seam; native listener wrapping is a test harness seam and should be confirmed against the concrete server composition before coding.

## Transport case table

Run the same focused behavior rows on each protocol and all four SQL engines: PostgreSQL 16, PostgreSQL 18, MySQL 8.4, MariaDB 11.4. The six base combinations per database are native/browser gRPC-Web/browser Connect crossed with database-only/shared Delivery. Gate the broader process-count matrix in the task acceptance table separately; keep this suite opt-in so a focused transport run does not silently launch the whole 2/8-process matrix.

| Case                                     | Deterministic setup                                                                                                                                                                                                                       | Required assertions                                                                                                                                                                                                                                                                                                           |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Activation ACK gates readiness           | Hold server-side Activate at the binding/service seam.                                                                                                                                                                                    | No ready indication/update before ACK; release gate and observe one ready transition. Avoid sleep-based readiness.                                                                                                                                                                                                            |
| Held Activate then immediate post        | Begin subscription and hold ACK; prove Activate reached fixture; release ACK; immediately post a typed Project command/event.                                                                                                             | First update arrives without requiring unrelated traffic; exact Project state/event identity matches SQL and stream.                                                                                                                                                                                                          |
| Idle readiness                           | Activate against empty SQL state and send no business traffic.                                                                                                                                                                            | Explicit successful Activate/ready signal occurs, and client remains connected for the configured idle observation interval without polling-derived updates.                                                                                                                                                                  |
| Cancel during activation                 | Hold Activate; issue `cancel`, iterator `return`, and/or `client.close` while pending, then release ACK.                                                                                                                                  | Every caller settles within bound; simultaneous teardown requests coalesce for that attempt; no update leaks after cancellation; active binding/stream count returns to zero. A later explicit retry after a failed Cancel remains allowed and is covered separately.                                                         |
| Concurrent teardown and Cancel           | After readiness, invoke explicit Cancel, iterator return, and client close concurrently; gate the server Cancel if needed.                                                                                                                | No duplicate Cancel, deadlock, or hanging close; repeated teardown settles idempotently; fixture reports no live registration/session after release.                                                                                                                                                                          |
| Same-handle Cancel retry                 | After readiness, make the first explicit Cancel RPC fail transiently; call `cancel()` again on the same handle and let the next Cancel succeed.                                                                                           | First attempt surfaces its failure; the later call is permitted and succeeds on the same public handle; simultaneous calls during either attempt coalesce; successful cleanup is idempotent; no remote registration remains. Do not treat sequential retry after failure as duplicate cancellation.                           |
| Stream reconnect                         | After readiness, inject a retryable stream failure, allow configured reconnect/retry, then publish one update.                                                                                                                            | Assert the documented reconnect contract independently from Cancel retry, with exact retry count, one logical update, and no duplicate handler work.                                                                                                                                                                          |
| Gateway fanout readiness                 | Have one logical subscription resolve to multiple backend subscription children; hold one child Activate ACK while allowing another child to ACK. Then run a separate case where one child activation fails after a sibling was admitted. | Overall readiness is withheld until every required child has ACKed. On partial activation failure, every already-admitted child is canceled/cleaned, failed child is not leaked, and the aggregate activation settles within bound. Assert child activation and cleanup counts.                                               |
| Permanent failure and close bounds       | Inject a non-retryable Subscribe/Activate/stream error, then separately hold a call beyond the configured close bound.                                                                                                                    | Terminal error settles predictably; no retry after permanent failure; close resolves/rejects within configured bound; no leaked registrations or unhandled library promise rejection.                                                                                                                                         |
| Event publication to multiple recipients | Subscribe two distinct ProcessManager recipients and a Projection using valid Project workflow fixture messages. Fail one recipient after another recipient has committed, then retry the same Event ID/bytes.                            | Each accepted recipient is counted; committed prefix remains visible; failed recipient remains retryable; no Command rerun; eventual states are correct and duplicate processing is excluded by the documented dedup window. This is Event publication acceptance, separate from backend subscription-child fanout readiness. |
| Cancel publication race                  | Publish while cancellation is gated at the service/binding seam.                                                                                                                                                                          | A publication linearized before Cancel may be delivered once; after Cancel completion no later update arrives; SQL and fixture counters identify which side won.                                                                                                                                                              |

## Fault injection and observations

The browser gateway's injected `SubscriptionBindings` is the cleanest ACK/cancel gate: use deferred promises around delegate calls, record invocation order, and release every gate in test cleanup. The binding delegates backend work through the subscription creator; instrument or wrap that test fixture boundary to count each child Activate and Cancel. For backend stream faults, use a test server/transport adapter that returns real Connect status errors or closes the stream; keep client-facing calls on the actual protocol transport. For SQL fanout/write faults, reuse the existing MySQL admin-trigger pattern in `packages/storage-mysql/test/mysql-integration.test.ts`; implement an equivalent PostgreSQL trigger only if the target write path can be identified precisely. Prefer a scoped test database trigger to rewriting source or wrapping storage internals. Record event/recipient IDs, SQL rows, process PIDs, retry count, child activation/Cancel counts, and final resource counts. Ensure fault removal occurs in `finally`.

Existing managed Delivery file gates are useful models for deterministic held work, but their current gate controls Delivery shard snapshot/admission, not subscription Activate. Reuse the pattern, not its private source transform. No existing harness currently provides one unified observation surface for native and browser active-subscription counts; the fixture must record those counters itself.

Keep this suite under the existing opt-in external-service policy. Add only the required new test path to `scripts/test-inventory.mjs`. Follow the existing package live-test conventions:

Do not execute any reference-folder investigation script or use its installed snapshot/hooks.

## Fail-fast gates

Before any full matrix run, assert at startup: selected endpoint responds; expected engine/version matches; all required databases exist; exactly one target protocol and Delivery mode selected for focused runs; process count is supported; and every generated fixture schema is imported from the worktree build. Put all held promises behind `try/finally` release. Every case must have a bounded timeout and assert cleanup counts. A failed setup assertion is an error, never a skipped acceptance. Report protocol, SQL image/version, Delivery mode, process PIDs, exact event/recipient IDs, and elapsed times alongside each acceptance result.
