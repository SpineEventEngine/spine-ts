The four-provider/two- and eight-process matrix remains pending. The PASS rows above are PostgreSQL 16, two-process smoke evidence, not cross-provider or eight-process evidence. The shared-memory case demonstrates volatile pending work loss, while the acknowledgement case demonstrates at-least-once handler execution across a process crash. Within a live attempt, acknowledgement retries do not deliberately rerun a successful handler. `result.json` now records FAIL with resource identity and runtime-tree/source provenance before cleanup errors are reported; earlier RED runs predate that correction and retain stdout/structured snapshots instead.

The retained-window extra rows are distinct Inbox UUID receipts admitted by simultaneous same-ID repairs, because `Inbox.receive()` allocates a new storage ID and `InboxStorage.write()` only deduplicates that exact ID. They carry the same saved Event bytes and typed recipient. `DeliveryPageDeduplication` later removes same-signal/typed-target pending duplicates when a retained delivered row or its process-local recent cache matches; in run `797c...`, the extra pending rows had all disappeared by the first five-second cleanup sample, before their 30-second retention elapsed. After SQL cleanup, the same surviving worker still held its in-memory cache for Portfolio and ProjectProjection; the warm final repair's new rows were removed without handler entry. This cache is neither durable nor an exactly-once guarantee. The cold-process test deliberately starts fresh PIDs after SQL cleanup and compares each method's entry count to the immediately pre-repair count, so it measures permitted repeat execution without attributing earlier pending receipts to the final repair.
