# Framework documentation review

## Finding

**P2 — The browser extension guide says subscription readiness follows an active wire, but readiness requires a successful matching ACK.** Its lifecycle diagram transitions `connecting --> connected: wire active` ([`docs/BROWSER_CLIENT_AUTH_EXTENSION_GUIDE.md:84`](../../../../../docs/BROWSER_CLIENT_AUTH_EXTENSION_GUIDE.md)). The client only reports `connected` after receiving a matching response-only successful ACK; an idle subscription can become ready without a business update, while malformed, mismatched, failed, or missing ACKs do not establish readiness ([`packages/client-web/REFERENCE.md:26`](../../../../../packages/client-web/REFERENCE.md), [`docs/api/README.md:146`](../../../../../docs/api/README.md)). The guide's simplified transition can lead extension authors to treat transport establishment as application readiness. Replace the transition label with the matching successful ACK and note that no business update is needed.

**P2 — Public `DeliverySupervisor.close()` timing and its non-total bound are not documented.** The server API index and references expose `DeliverySupervisor` and say to close it before its source/storage, but they do not describe `close({ graceMs })`. The public option defaults to 30,000 ms and applies separately to the active-work grace and release-cleanup wait ([`delivery-supervisor.ts:402`](../../../../../packages/server/src/delivery/delivery-supervisor.ts), [`delivery-supervisor.ts:801`](../../../../../packages/server/src/delivery/delivery-supervisor.ts)). After those waits, `#closeNow()` still awaits active work that remains in flight ([`delivery-supervisor.ts:425`](../../../../../packages/server/src/delivery/delivery-supervisor.ts)); an already-entered callback or storage effect that never settles can therefore keep direct supervisor close pending beyond both grace periods. The docs separately give the five-second `BoundedContext` deadline and 30-second managed-server deadline, which are different lifecycle paths and do not describe this public direct-close API. Document the per-phase grace and that it is not a hard total close deadline.

No P1 findings. A previous P2 concerning an atomic cleanup guarantee in `packages/server/REFERENCE.md` was corrected in the current worktree; the reference now accurately says deletion does not compare the row snapshot or recheck the shard session after eligibility validation ([`packages/server/REFERENCE.md:861`](../../../../../packages/server/REFERENCE.md)). Other reviewed claims about prepared Entity writes, immutable retries, Event publication and explicit repair, processing versus acknowledgement failures, paging, error-cause privacy, and in-memory Delivery durability match the inspected implementation and current references.
