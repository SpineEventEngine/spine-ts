# Code-derived account: base `658da1cdddcb8fd40f9205b1c200abc3a58dd62e` to this worktree

This account is based on source, Protobuf, package, and launcher diffs and selected before/after execution paths. It does not infer the original task intent or claim exhaustive verification. Paths and line numbers below refer to the current worktree unless prefixed `base:`.

## Behavior visible before the change

- Event batches used strict absent-ID insertion, rolled back a batch prefix after a collision, and exposed `appendAllWithRollback()` with a one-shot deletion token (`base:packages/storage/src/event/event-store.ts:117-148,170-195`). This could turn a later failure into deletion of already-written Events; the source did not make the Event and all other Entity records one atomic unit on every provider.
- MySQL Entity commits used a coordinator and shared connection, with transactional behavior where the table engine supported it (`base:packages/storage-mysql/src/mysql/storage-factory.ts:839-863`). The changed provider contract explicitly acknowledges that other provider/engine paths could retain partial writes (`packages/storage/src/internal/entity-commit.ts:25-32`).
- Remote Inbox continuation was reconstructed from a timestamp page. It had to find the exact previous row within that page and rejected a full page ending in a timestamp tie, so an otherwise valid ordered backlog could fail to continue safely (`base:packages/delivery-client/src/remote/adapters.ts:107-132`).
- The default reception-failure action marked a failed row delivered (`base:packages/server/src/delivery/delivery-monitor.ts:204-212`). Thus a failed endpoint could be acknowledged under the default policy. This is a direct source-level observation, not a claim about every configured monitor.
- The browser subscription's `activate()` resolved after opening an activation iterator and launching background consumption, before confirming a server readiness response; a failed `cancel()` promise was cached for the handle (`base:packages/client-web/src/client/client.ts:1010-1062`). System Event publication used the ordinary follow-up Event route, which could persist through the System bus and dispatched with one contained attempt (`base:packages/server/src/runtime/signal-publisher.ts:127-160`).

## Resulting execution path and contracts

- Entity commit input now carries canonical delivery `events` separately from optional diagnostic history, is cloned before provider I/O, and has an explicit ordered, non-transactional contract (`packages/storage/src/internal/entity-commit.ts:25-74,76-145`). MySQL, PostgreSQL, and Datastore write state history, diagnostic history, immutable delivery Events, then current state; they replay the captured input once for selected driver errors (`packages/storage-mysql/src/mysql/storage-factory.ts:814-877`, `packages/storage-postgres/src/postgres/entity-commit.ts:183-246`, `packages/storage-datastore/src/datastore/entity-history.ts:149-222`). The change makes Event IDs stable across a retry, but an Event's presence does not prove that current state was saved (`packages/storage/src/internal/entity-commit.ts:127-132`).
- `EventStore.append()` and `appendAll()` now accept an identical complete Event already stored under the same ID and retain a completed prefix after a later failure. `accept()` and `acceptThenAppend()` still require a new ID; the latter checks, runs the callback, then attempts the atomic single-record insert, so a competing callback can also run before one insertion loses (`packages/storage/src/event/event-store.ts:88-147,169-205,317-365`). The public `EventRollback` type and `appendAllWithRollback()` method disappear from the storage root; the constructor gains an optional record group (`packages/storage/src/index.ts:16`, `packages/storage/src/event/event-store.ts:59-70`). These are incompatible TypeScript API removals even though immutable append becomes retryable.
- The storage `RecordFilter` contract now explicitly treats an array as scalar membership choices, including an empty array that matches no records; MySQL and PostgreSQL emit parameterized null-safe disjunctions or `1=0` rather than comparing the entire array as one SQL value (`packages/storage/src/record/record-query.ts:67-73,109-117,177-192`, `packages/storage-mysql/src/mysql/record-storage.ts:850-860`, `packages/storage-postgres/src/postgres/record-storage.ts:774-787`). The public filter still types `value` as `unknown`, so its declaration does not statically enforce the documented scalar-only inputs. The in-memory provider already treated arrays as choices and now calls the same helper (`packages/storage/src/memory/tenant-records.ts:314-320,585-594`). Normalized query plans retain literal array equality, as the `RecordFilter` documentation states (`packages/storage/src/record/record-query.ts:188-192`).
- MySQL and PostgreSQL provider wrappers now retain the original driver failure in `Error.cause` while keeping their outward messages stable (`packages/storage-mysql/src/mysql/errors.ts:30-49`, `packages/storage-postgres/src/postgres/errors.ts:40-63`). This gives the bounded SQL retry classifiers access to driver codes through provider wrappers (`packages/storage-mysql/src/mysql/storage-factory.ts:839-853`, `packages/storage-postgres/src/postgres/entity-commit.ts:202-217`); code that examines the public error object can also access the original cause, so the safe-message guarantee does not extend to the entire error object.
- Committed Event, reactor Event, stored redispatch, and System Event publication now return an internal `StoredEventPublication` outcome after at most three attempts separated by 100 ms. System publication validates and, when configured, appends to its separate store _before_ stored-event dispatch; it retries the same captured Event if append fails. `attempts` counts entered dispatch calls, so an append failure may produce `FAILED` with zero dispatch attempts (`packages/server/src/runtime/signal-publisher.ts:24-60,183-285,426-459,503-527`). Canonical `EventStore.append()` can confirm an identical retry, whereas bus delivery still may have side effects before failure. The bus checks cancellation and terminal closure between recipient acceptance/dispatch steps, but an already entered recipient is not undone (`packages/server/src/bus/event-bus.ts:464-517`). Hence a later publication attempt may repeat an earlier recipient effect. Produced Command and rejection Event handling remain on the separate contained, single-attempt `#publish` path (`packages/server/src/runtime/signal-publisher.ts:148-181,392-414`). These outcome types are exported by their source module but that module is absent from the package's declared root/subpath exports (`packages/server/package.json:14-39`); they are package-internal in the published API layout.
- The default delivery monitor now leaves a failed reception pending; the finite drain blocks that target when the selected action does not durably acknowledge it. Successful endpoint processing followed by acknowledgement failure is retried up to three times for acknowledgement alone, without deliberately repeating the endpoint in that same drain (`packages/server/src/delivery/delivery-monitor.ts:60-113,197-244`, `packages/server/src/delivery/delivery.ts:574-639`). This reduces immediate loss under the default monitor, but does not establish exactly-once endpoint effects: if acknowledgement still fails, a later drain may process the pending row again. The supervisor now suppresses repeated _observed_ failed-shard runs until periodic recovery and lowers its default recovery interval from 30 seconds to 10 seconds; explicit notification is handled separately (`packages/server/src/delivery/delivery-supervisor.ts:309-328,352-380,478-503,555-560,623-663,775-779`).
- Remote Inbox paging adds `InboxReadService.ReadPage`, `InboxCursor`, and `ReadInboxPage` in a new Protobuf file, exported from the delivery-server proto entry point and registered by the delivery server (`packages/proto/proto/spine/delivery/inbox_read.proto:25-44`, `packages/proto/src/delivery-server/index.ts:22`, `packages/delivery-server/src/server/delivery-server.ts:250-252`). The cursor is exclusive `(when_received, version, message_id)`; server sorting and comparison use bytewise UTF-8 ID order (`packages/delivery-server/src/core/inbox-service.ts:97-121,418-429,544-559`). The client now calls this service, adds `DeliveryReadPageOptions.after`, and checks response ordering, duplicate IDs, and advancement (`packages/delivery-client/src/client/types.ts:319-339`, `packages/delivery-client/src/client/client.ts:286-386`). It requires a server offering the new RPC; the client has no fallback to the older timestamp-only RPC (`packages/delivery-client/src/client/client.ts:295-307,662-668`). Existing wire message fields were not renumbered by this added file, but mixed-version deployment of a new client against an old server changes behavior.
- The remote adapter now applies one aggregate read deadline across pages and lets cancellation settle its outward wait even if a supplied transport stalls (`packages/delivery-client/src/remote/adapters.ts:101-165,195-223`). This does not prove that underlying transport work stops. The remote remove methods no longer accept a session parameter and issue removal by ID without their former read-and-compare step (`packages/server/src/delivery/delivery-ports.ts:99-117`, `packages/delivery-client/src/remote/adapters.ts:265-299`). Inference: the result boolean cannot certify that the row still matched the earlier snapshot when deletion occurred; callers that depended on the old structural port signature must adapt.
- `BoundedContext.republishEvents()` is newly exported as a bounded, process-local repair API with 1–100 distinct IDs, optional tenant scope and cancellation, and per-ID `ADMITTED`, `FAILED`, `NOT_FOUND`, or `CANCELLED` outcomes (`packages/server/src/index.ts:25-30`, `packages/server/src/context/bounded-context.ts:433-471,1234-1262`). It reads exact IDs from domain and System Event families, rejects a cross-family ID collision, and submits stored Events to their buses (`packages/server/src/context/bounded-context.ts:1272-1339`). `ADMITTED` means the dispatch was admitted, not that every recipient completed; repeat dispatch may repeat recipient effects. It cannot prove that a domain Event belongs to a completed Entity save, and it is not automatic backlog scanning (`packages/server/src/context/bounded-context.ts:1234-1241,1264-1295`).
- The public Command RPC still returns its existing stable Ack codes for invalid, unsupported, tenant-mismatched, and failed posts. For unexpected post failures it now emits a structured server error with command and context correlation plus only allowlisted SQL codes found through a bounded `cause` walk; those driver details are not added to the Ack (`packages/server/src/services/spine-services.ts:287-373,2151-2207`). The native subscription server emits a response-only successful activation update after attaching the record (`packages/server/src/services/spine-services.ts:489-514,523-565`). The browser client now waits for and validates that ACK's topic and ID before `activate()` resolves or reports `connected`; it rejects a later duplicate ACK, and reconnects perform the same handshake before entity resynchronization or Event gap signaling (`packages/client-web/src/client/client.ts:1036-1048,1060-1144,1230-1258,1310-1335`). `cancel()` and per-wire cancellation clear failed remote-attempt promises so another attempt can be made, although local streams are already stopped (`packages/client-web/src/client/client.ts:1006-1019,1146-1159,1521-1535`). The browser's prior return-on-stream-open behavior and permanently cached cancellation failure are therefore changed public lifecycle behavior; old servers without the new ACK will not satisfy activation readiness.
- Managed shutdown now has a configurable `shutdownTimeoutMs`, a child `delivery-drained` acknowledgement, staged relay cleanup, and force cleanup when its absolute deadline expires (`packages/server/src/server/managed-server-application.ts:165-174,1184-1245,1263-1330`). Context shutdown similarly starts one deadline, fences later queued work when it expires, and continues bounded close phases (`packages/server/src/context/bounded-context.ts:1423-1496,1541-1590`). These are bounded _outward waits_: entered provider or application work can still settle afterward (`packages/server/src/context/bounded-context.ts:1553-1576`). Coordinator subscription intake rejects new requests while draining and relays are closed after child delivery drains (`packages/server/src/server/node-coordinator.ts:481-600`, `packages/server/src/server/managed-server-application.ts:1292-1322`). This extends scope beyond SQL record writes.

The workspace advances from `2.0.0-snapshot.22` to `.23`, including internal dependency pins (`package.json:3`, `packages/server/package.json:3,46-65`). This is a material launch/config expansion, separate from storage semantics.

The principal tradeoff is deliberate visibility of partial progress: immutable rows can survive failed saves, and retries can confirm identical rows, but no cross-record transaction is promised across the changed providers. Repair requires exact IDs whose completed-save provenance is known to the caller, and dispatch admission cannot guarantee recipient completion. Pending delivery plus finite acknowledgement retries favors later recovery over silent default acknowledgement, while leaving possible duplicate endpoint effects when a prior invocation succeeded but its acknowledgement did not. No full test suite, live service, or deployment verification was run for this independent account.
