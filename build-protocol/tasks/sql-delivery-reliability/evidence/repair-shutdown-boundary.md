# Known-ID repair shutdown boundary

An entered exact-ID `EventStore.read()` previously prevented `republishEvents()` from settling after caller abort. `evidence/repair-read-cancel-red.log` records the 25 ms bounded test returning `timed-out`. The implementation now races the exact read against caller cancellation and context closure, observes the eventual provider promise, and reports `CANCELLED` for the current and remaining IDs. The seven focused repair tests and tooling typecheck pass after that change.

A separate never-settling recipient can still prevent **whole-context close** from finishing. The call chain is `BoundedContext.close()` → `#drainWork()` → `ContextParts.drainContextWork()` → `EventBus.drain()` and `SignalPublisher.drain()`. Both await admitted recipient work without a deadline. Repair publication invokes `EventBus.postStored()`, so a recipient promise that never settles remains admitted to those drains even if a repair-level timeout were added. A repair-only `Promise.race` would return a caller outcome while the bus still retains the handler and close still waits. The accepted architecture requires a smallest compatible bounded close/cancellation design before claiming shutdown bounds for this case; no broad bus change has been made in this slice yet.
