# Orders and Projects activation-ack triage

## Finding

The Orders workload failure is caused by a low-level client treating the first `Activate` stream item as the domain update. `SpineServices.#activate` now first yields a response-only readiness acknowledgement (`subscription` and successful `response`, with no `update` oneof), then yields items from `record.delivery` ([spine-services.ts:489](/Users/armiol/.codex/worktrees/sql-delivery-reliability/spine-ts/packages/server/src/services/spine-services.ts:489)). That first item is valid activation success, not an `OrderSummary` or `ProjectSummary` delivery.

In both load runners, `startSubscription()` starts the iterator and saves exactly one `iterator.next()` as `firstUpdate` ([Orders:281](/Users/armiol/.codex/worktrees/sql-delivery-reliability/spine-ts/examples/orders/src/load-runner.ts:281), [Projects:221](/Users/armiol/.codex/worktrees/sql-delivery-reliability/spine-ts/examples/projects/src/load-runner.ts:221)). Their `readSubscription()` functions test only that one value for a correlated Entity update and immediately throw otherwise ([Orders:361](/Users/armiol/.codex/worktrees/sql-delivery-reliability/spine-ts/examples/orders/src/load-runner.ts:361), [Projects:260](/Users/armiol/.codex/worktrees/sql-delivery-reliability/spine-ts/examples/projects/src/load-runner.ts:260)). They need to consume the readiness acknowledgement and continue reading until the correlated domain update arrives, subject to the existing deadline.

## Evidence and affected consumers

- `orders-10-users.log` records `failedUsers: 10`, zero aggregate success counters, and ten failures with `Order subscription update was not correlated to load-…`. This matches the source path above.
- `projects-10-users.log` records `failedUsers: 10` and zero aggregate success counters, but contains no `failureMessages`; the log alone does not establish its per-user exception. The Projects source has the same first-item assumption and correlation check, so it has the same source-level incompatibility with a response-only first item.
- Both load-runner result builders set acknowledgement, query, and delivery counters to the number of fully successful users ([Orders:201](/Users/armiol/.codex/worktrees/sql-delivery-reliability/spine-ts/examples/orders/src/load-runner.ts:201), [Projects:144](/Users/armiol/.codex/worktrees/sql-delivery-reliability/spine-ts/examples/projects/src/load-runner.ts:144)). Their zero counters therefore do not show that command submission or query visibility failed independently; each user is counted only after the whole run succeeds.
- The direct gRPC topology tests start `Activate` before posting, then assert only `update.done === false` ([Orders:81](/Users/armiol/.codex/worktrees/sql-delivery-reliability/spine-ts/examples/orders/test/topology.test.ts:81), [Projects:165](/Users/armiol/.codex/worktrees/sql-delivery-reliability/spine-ts/examples/projects/test/topology.test.ts:165)). The response-only acknowledgement satisfies these assertions, so the tests can pass without observing a domain update. Adapt them to assert a correlated domain update as well.

No workload was rerun for this triage. The Projects failure text remains unobserved in the supplied result log; its likely runtime symptom is an inference from the matching source pattern and the new service stream shape.
