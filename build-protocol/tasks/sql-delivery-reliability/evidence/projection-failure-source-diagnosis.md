## Smallest source-grounded failure hypothesis

The remote Inbox read has a deterministic full-page timestamp-tie failure. `RemoteInbox.#readPage` asks DeliveryServer for a time-anchored page and throws `DeliveryPagingError` when a full page's last two messages share `whenReceived` (`delivery-client/src/remote/adapters.ts:107–132`). DeliveryServer orders by receive time, version and UUID but exposes only the timestamp filter for page continuation (`delivery-server/src/core/inbox-service.ts:185–203,326–335`). The fixture puts both projection types on one shard, and separate app processes generate `Time.currentTime()` values using per-process millisecond/microsecond counters (`core/src/time/index.ts:58–68`). A timestamp tie at a full-page boundary can therefore leave the same page unreadable on every new attempt. An active supervisor run records the failure and gates source observations until the next ten-second recovery (`delivery-supervisor.ts:492–503,553–564`); recovery will encounter the same page while the tied rows remain. The DeliveryServer's 100-frame subscriber buffer can also close a busy watch and force recovery (`delivery-server/src/admin/admin-service.ts:263–277`), increasing reliance on that path.

This is a **confirmed source behavior under the timestamp-tie precondition**, not a confirmed cause of this run. The failed run lacks remote Inbox row order, receive timestamps, statuses, page responses, supervisor failures and shard observations. The 31/31 cutoff and single PID fit a stopped single-shard drain, but do not establish a tie, a watch failure, a stuck lease, or even that all 160 expected projection rows were written. No source evidence justifies changing persistence or claiming permanent Event loss.
