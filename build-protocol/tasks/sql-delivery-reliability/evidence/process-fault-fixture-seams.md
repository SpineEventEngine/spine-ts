# Project OS-process fault fixture seams

Read-only fixture/API analysis for deterministic process failures. Dispatch: orchestrator-dispatched test-analysis function, explicitly configured `gpt-6-luna` / `low`; runtime metadata introspection is unavailable. No build, test, database, or child process was run. This note scopes Project fixture additions and avoids repeating the general seam map in `remaining-live-fault-map.md`.

## Existing support

- `project-workflow.ts` has real `Project.create`, Planning/Staffing reactions, and Portfolio/Project projections. Every handler synchronously calls `onEntry` before `this.update`; `ProjectHandlerEntry` already includes method, correlation, recipient type URL, and base64 bytes of the correctly typed recipient ID.
- `project-worker.mjs` already exposes IPC `start`, `post`, `inspect`, `inspectDelivery`, and `close`. `inspect` reads all five SQL Entity states and reads `EventStore` envelopes, returning exact Event IDs, full-envelope binary bytes, and SHA-256. `inspectDelivery` reads each configured shard and returns Inbox ID, signal ID, target state type URL, status, and version. It should additionally return the typed target ID (`Any.typeUrl` and base64 `Any.value`) and signal payload type URL for exact fault-row selection.
- `project-process-smoke.mjs` already creates one random provider database per run, starts 2 or 8 actual Project OS processes, supports SQL-backed Inbox (`db-only`) and a separate shared-memory `DeliveryServer` child (`shared-memory`), can restart application processes, captures PIDs/logs/artifact hashes, and cleans children/database in `finally` with bounded close/TERM/KILL waits.
- Public repair is available on the started context: `await context.republishEvents({ eventIds: [eventId] })`. It accepts exact Event IDs, reads the stored Event, and returns per-ID status/attempts. No Command repost is required. `inspect` already supplies the stored full Event bytes before and after repair.

## Minimal test-only fixture delta

Prefer a purpose-built `project-process-faults.mjs` driver and dedicated integration test, reusing the worker, project workflow, provider selection, artifact fingerprinting, and cleanup helpers. Avoid adding fault branches to the ordinary smoke matrix. Add only these worker capabilities:

1. A `settings.handlerGate` descriptor selecting `{ correlation, method, recipientTypeUrl, recipientIdBase64 }`, plus a release-file path and a short deadline. In the existing synchronous `onEntry` callback, append and flush the JSONL entry first, then block that worker thread with bounded synchronous file polling until the release file appears or the deadline expires. This keeps the gate after observable actual method entry and before `this.update`, and lets the parent identify the exact PID to kill. Do not hold a generic gate that could pause unrelated Project IDs or recipient types.
2. An IPC `republish` action accepting only explicit `eventIds` and returning `context.republishEvents({ eventIds })`; it must not call `post`, scan history, or infer IDs. Continue using `inspect` for Event bytes and state snapshots.
3. Enrich `inspectDelivery` rows with `targetIdTypeUrl`, `targetIdBase64`, and signal payload type URL. Keep the row identity `{ messageId, shard }`, `signalId`, target state URL, typed target ID, label, status, and version together in JSONL/snapshots. Those values plus the logged Project entry identify a row by domain ID rather than by position or a guessed byte layout.
4. Add one scoped provider fault installer in the purpose-built driver. Read the actual generated Inbox table layout from `inboxRecordSpec` / provider table resolver and match the declared `signal_id`, `inbox_id`, `message_id`, and `status` columns. Inbox storage uses context `${context.name}.delivery.inbox`, record type `spine.delivery.InboxMessage`, and declares columns `inbox_id`, `signal_id`, `shard_index`, `shard_total`, `status`, `when_received`, `version`, and `message_id`. Do not hard-code a table guessed from context name; resolve/quote the per-provider table/schema from that metadata or admin catalog before installing a trigger. Use trigger names containing the run UUID and always drop them in `finally` before dropping the isolated database.

## Four process cases

**Kill after actual handler entry, before its effect.** Start the normal SQL Inbox mode with the selected handler gate. Post exactly one unique-ID `CreateProject`, wait for the flushed entry matching its full correlation and typed recipient ID, record its PID, and SIGKILL that child before releasing the gate. Assert the entry exists for the killed PID while the corresponding recipient state is absent; `Project.create` and its saved Event are separately visible if the selected method is a downstream recipient. Restart all app OS processes from the same isolated database and artifact hashes; do not repost the Command. Assert the pending work is processed, the expected recipient state appears, the saved Event ID/bytes remain unchanged, and entry/Command counts distinguish the killed attempt from recovery. Keep the existing hard process watchdog and guarantee the gate deadline releases a forgotten gate.

**Kill after a successful Entity save, before Inbox acknowledgement.** Do not use the pre-update handler-entry callback for this boundary. Install a run-scoped `BEFORE UPDATE` Inbox trigger that blocks only the selected row's transition to `DELIVERED`, selected by exact Event `signal_id`, target type URL, typed target-ID bytes, and known message ID. After the trigger is reached, poll from a separate process until the recipient Entity state is visible in SQL while that exact Inbox row remains `TO_DELIVER`; then SIGKILL the handling app PID while it is blocked in the acknowledgement update. This proves the handler save committed before ack was attempted. Restart app processes on the same DB after removing the trigger. Assert one initial handler entry, a recovered second entry where expected, final delivered status, and unchanged Event bytes. Provider-specific trigger syntax (especially a bounded blocking trigger for MySQL) must follow existing provider admin-trigger patterns; keep the blocking window short and hard-bounded.

**Fail one recipient Inbox admission after a saved Event and a successful prefix, then restart every app process and repair by exact ID.** In normal SQL Inbox mode, install a scoped `BEFORE INSERT` failure for the one saved Event ID and one chosen recipient, matched by `signal_id`, Inbox target state URL, and the generated typed target-ID encoding. Choose a recipient after the known first prefix in the fixture’s declared repository/event-routing order; verify the prefix row exists and the failed recipient row does not before continuing. Post once, then verify the saved Event by `EventStore.read`/`inspect` and persist its Event ID plus exact envelope bytes. Remove the insert trigger, close and stop every application OS process, start fresh processes against the same database, and call `republish` once with that saved ID. Assert `create`/Command entry remains exactly one, Event ID and full Event bytes are unchanged, missing recipient state/admission converges, and the recipient entry counts show possible repeated dispatch to already admitted recipients rather than asserting no replay of the prefix. No automatic historical replay or broad catch-up call is involved.

**Kill and restart shared in-memory Delivery with accepted pending work while SQL business data survives.** Use shared-memory mode and the exact handler gate on one downstream recipient. After the Command/Event save, wait until `inspectDelivery` sees the corresponding Event signal and typed recipient row as pending while the handler entry proves one app is paused before its state effect. Record the delivery PID and row ID, then SIGKILL the Delivery child and all app children. Start a fresh `DeliveryServer` child and all app processes against the same SQL database but the new endpoint. Assert the original Project state and exact Event envelope still exist in SQL, the old in-memory Inbox row is absent from the new Delivery instance, and no Command was rerun. This is the direct volatility demonstration; do not state that SQL-backed Inbox rows are lost.

## Fault rows and evidence bounds

- Domain selectors use the fixture’s generated schema and identifier bytes (`ProjectIdSchema`, `PlanningIdSchema`, `StaffingIdSchema`, `PortfolioIdSchema`), never a different ID type with matching wire fields. Inbox row selectors use the target Any's actual type URL/bytes and stored `signalId` (the Project Event ID for event delivery; `Repository` creates Event Inbox records with `signalId: eventId.value`).
- The Inbox record source type is `spine.delivery.InboxMessage`; the storage layer’s resolvers derive physical names from record metadata. Resolve the actual table/catalog and column type before fault injection; `inbox_id` is a typed Protobuf value, so compare the provider’s encoded column according to the generated RecordColumn mapping rather than treating it as an arbitrary JSON/string field.
- One fault run should use one isolated random database, one Project Command, two app processes, and at most one Delivery child. Keep gate waits ≤10 seconds, each request ≤15 seconds unless it is an explicit bounded state poll, each blocking trigger ≤30 seconds, the whole driver under the existing 210-second watchdog, and retain the current graceful-close/TERM/KILL escalation. `finally` must remove trigger/function, release gate files, stop/reap every recorded PID, close admin connection, and drop the database; the test checks durable cleanup evidence.

## Seam conclusion

No production API addition appears necessary. Exact-ID Event repair, Inbox inspection, real Project handler entry, SQL state inspection, and process kill/restart are present. The missing determinism is fixture-only: a per-entry bounded gate, typed target identity in row snapshots, an exact-ID repair IPC action, and provider-scoped Inbox triggers for admission/ack boundaries. A potential implementation uncertainty remains the provider encoding/catalog representation of the Protobuf `inbox_id` column and the safest bounded MySQL trigger wait; resolve those from existing provider DDL/admin-trigger patterns before writing that fault driver. This analysis does not claim the scenarios have run or establish production behavior.
