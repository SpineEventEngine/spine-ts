## Findings

1. **P2 — Distinct tuples with one Inbox identity pass peer validation.** `packages/delivery-client/src/client/client.ts:322-344` checks that each decoded tuple increases, but never records message IDs. A malformed `ReadPage` response containing the same `id.uuid` twice with a later `whenReceived` or `version` passes `#compareInbox`, so direct `readPage()` and `RemoteInbox.read()` expose a duplicate logical Inbox message. D-0132 expressly requires unique identities before consumption; the existing repeated-page test uses an equal tuple and does not cover this case. Reject a repeated ID within one page independently of tuple order and add a fake-peer test with one ID at two increasing tuples. This is a peer-contract defect; the normal in-memory server's map cannot produce duplicate IDs in one static page.

2. **P2 — An invalid peer timestamp escapes as an input TypeError rather than a protocol error.** The new `DeliveryClient.readPage()` maps peer rows through `DeliveryMessageCodec.decode` at `packages/delivery-client/src/client/client.ts:308-313`. That decoder calls `DeliveryRequestCodec.timestamp` for `whenReceived` at `packages/delivery-client/src/wire/codec.ts:394`; the shared validator throws `TypeError` for out-of-range seconds or nanos at `:1135-1145`. A protobuf peer can encode such a Timestamp, so the page is malformed but fails with the public input-validation error instead of `DeliveryProtocolError`, contrary to D-0132's malformed-peer rule. Normalize this response-side timestamp failure at the page boundary (without changing request validation) and test a fake peer response with invalid `whenReceived`.

## Clean paths and limits

Server sort and cursor seek use the same receive-time/version/unsigned UTF-8 ID order. The cursor is a tuple predicate rather than a lookup, so deletion and status-only changes do not block static continuation. RemoteInbox advances from the last raw row after filtering, uses one monotonic deadline, races entered noncooperating page promises with cancellation, and removes its timer/listener. The direct client enforces requested page count, shard, ascending tuples, exclusive lower bounds, encoded response size when serializable, and one non-retried `UNIMPLEMENTED` failure with its cause. The new service is wired to the same bounded in-memory state and response-size cap. The server's whole-state selection has a configured retained-state bound and follows the preexisting Inbox read pattern; no optimization finding is raised.

The matrix fixture persists the latest and all-worker state observations, includes the distinct projection single shard in capped per-shard Inbox diagnostics, and retains the exact database/run identity before creation. Its adapter reports cleanup only from a durable completed cleanup record; forced termination with no record remains unknown. No confirmed defect was found in those changed diagnostic paths. The production fix still needs an instrumented workload repeat before any claim that it explains the earlier missing projections.
