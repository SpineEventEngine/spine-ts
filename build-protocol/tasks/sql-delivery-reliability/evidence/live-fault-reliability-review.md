## Finding

1. **P2 — A connection-close failure skips removal of the test database.** In `packages/server/test/delivery/inbox-provider-faults.integration.test.ts:215-223`, `withSqlDelivery` awaits `sql.end()` and then drops its UUID database in the same `try` block. If `sql.end()` rejects while cleaning up a faulting connection, control jumps directly to `admin.end()` and never attempts `DROP DATABASE`. Likewise, a synchronous `factory.close()` failure at line 216 skips both later cleanup steps. That leaves an exact test-created database behind and can obscure the original test failure with a cleanup error. Make connection/factory close and exact-database drop independent best-effort steps, retain all failures, and keep the drop constrained to the generated `sqlrel_delivery_<UUID>` database. A controlled cleanup-failure test should show the drop is still attempted when `sql.end()` rejects. The current green provider cases exercise normal cleanup only.

2. **P2 — The monitor catches the test's cause and acknowledgement-phase assertions.** The acknowledgement-exhaustion test asserts `causeCode(failure.error)` and `repeatDispatching().execute()` inside `onReceptionFailure` at `packages/server/test/delivery/inbox-provider-faults.integration.test.ts:135-142`. Production `delivery.ts:613-616` calls this hook through `safelyValue`, which catches a rejection and substitutes `leavePending()`. If either expectation fails, `observedFailures` has already incremented and the outer result, handler count, SQL attempt count, and pending-row assertions may still pass. The test therefore does not establish the claimed driver cause or the no-repeat acknowledgement action. Capture the observed cause and repeat outcome without assertions inside the callback, then assert them after `run()` returns; keep the exact outer handler/attempt/row checks.

## Confirmed behavior and limits

The six cases distinguish default failed processing with unrelated handler progress, throwing monitor, selected failed repeat, selected successful repeat, acknowledgement retry success, and acknowledgement exhaustion. Handler-entry and pending/removed-row assertions match those outcomes. `FailedReception` exposes no public phase field; the intended rejected `repeatDispatching()` check can establish the acknowledgement path only after its result is asserted outside the safely caught callback. PostgreSQL sequence and MySQL/MariaDB MyISAM counters persist across trigger rejection; expected three versus nine UPDATE attempts reflect the nested CAS retry. The injected 40P01 / 40001-1213 signal is a controlled deadlock-class error, not proof of an engine-detected lock cycle. The opt-in inventory and provider commands include the suite without adding it to ordinary CI. This test does not establish admission INSERT failure, OS crash, or full process/transport behavior.
