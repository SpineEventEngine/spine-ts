# Retained Delivery takeover: performance and reliability review

Review scope: the frozen takeover fixture and wrapper, the `project-worker.mjs` gate-candidate change, and their three inventory entries. Existing performance/reliability reviewer profile: explicit `gpt-6-sol` / `medium`; actual runtime self-introspection is unavailable. This was a read-only source/evidence review; no source edits, builds, tests, or service actions were performed.

## Finding

- **P2 — Complete the typed pending-Event assertion.** In `packages/server-blackbox-tests/test-fixtures/project-shared-takeover.mjs:205-215`, the selected Inbox row is found by saved Event ID and recipient identifier, but its `targetTypeUrl`, `signalTypeUrl`, and `signalValueSha256` are not compared with the selected state schema, `EventSchema`, and the saved original Event bytes. The same incomplete lookup is used after the kill at lines 249-253 and before stale release at lines 269-279. Consequently the test can pass while the row attributed to the gated handler contains a different signal payload or target message type. It can also select one of multiple matching rows because `find` does not establish uniqueness. Derive the selected Planning/Staffing state type URL, require exactly one row for the full typed key, and assert the Event Any type and value hash against `original.sha256` before the kill and after the kill. The eight recorded runs happen to show the expected state type, Event Any type, and matching hash in their saved Inbox observations; this is an assertion gap, not evidence of a current production mismatch.

## Confirmed evidence and limits

- The eight `takeover-*-default-final1.log` rows cover PostgreSQL 16/18, MySQL 8.4, and MariaDB 11.4 at two and eight replacement workers. Each run records a real `SIGKILL` of the gated worker, a separate retained Delivery server PID, distinct replacement PIDs, the same pending message ID before and after the kill, one Command handler entry, two selected recipient entries across old/new PIDs, final business states, and unchanged saved Event ID/binary/hash. The `cleanup.json` records show all worker/server exits and database drops without errors. The eight final result files match their corresponding log JSON; the deep runtime hash is the same across those rows.
- The default runs observe the selected state false and its row `TO_DELIVER` near 35 seconds, followed by completion near 60–61 seconds. Those timestamps are consistent with the 60-second supervisor stale-session age and a separate 10-second recovery scan. They are observations, not a direct trace of which timer invocation released the session. The processing-timeout-10 wrapper run also passes and completes near 60 seconds; it does not establish a 10-second takeover.
- The fixture's `artifacts` and runtime-tree hashes are recorded before worker launch, while `project-worker.mjs:179-183` returns each worker's artifact hashes without the driver comparing them. The records therefore identify a stable sampled tree, but they do not by themselves prove every child loaded those exact bytes if compiled files changed during a run. The review assumes the stated frozen dist reservation. The test does not establish exactly-once Event delivery, automatic discovery of missing historical work, Delivery-server restart durability, or an application-wide availability guarantee.
- The test wrapper bounds ordinary child IPC requests, observation, shutdown escalation, and its isolated driver process. A wrapper timeout can terminate the driver before its database cleanup finishes; `cleanupState` then reports cleanup as unverified. The final successful rows show clean teardown, while abnormal timeout cleanup remains a limitation rather than a claimed successful path.
