# Nonblocking process-fault gate: reliability review

**Disposition:** Clean. No actionable P0–P3 finding in the three changed test fixture files. This is a bounded review of the uncommitted gate correction, not acceptance of the full provider/process matrix or release gate.

**Review profile:** Existing performance/reliability concern, explicitly dispatched as `gpt-6-sol` / `medium`. Runtime self-introspection is unavailable on this surface; the configured profile and dispatch are the available evidence.

The worker writes each handler-entry record synchronously, then returns a Promise that polls the selected release file with a 10-second deadline. All five workflow methods await that callback before applying an effect or returning an Event; the Create method is included for the volatile-loss crash. Gate timeout rejects the handler Promise, and process death ends pending timers. The driver keeps the exact Planning recipient and pending Inbox row checks, confirms an acknowledgement trigger attempt and pending SQL status after killing all old workers, and requires one fresh Planning entry and one audited acknowledgement after restart. The new phase log adds observations without relaxing these assertions.

The failed eight-process run `fac352afed684a23aa75c4149a14f810` recorded its first Planning entry more than ten seconds before trigger installation and two old-worker Planning entries before the kill. It is invalid placement evidence, not an acknowledgement-only replay result. In final run `e91e588c7ca5476f88d4b4efd37da89e`, trigger installation followed the first entry by 99 ms; the saved Planning state and exact row still pending were observed before the selected worker was killed. Its pre-kill record has one Planning entry, the SQL trigger recorded one attempt, the row remained pending, and the fresh workers made one subsequent Planning entry and one audited acknowledgement. Event identity and bytes were retained. The PostgreSQL 16 two-process acknowledgement, eight-process before-effect, and two-process shared volatile-loss controls passed; the latter still observes loss of the second accepted Command after Delivery and app process death.

The gate uses a bounded timer and does not create an unbounded polling loop in a surviving worker. No service or build was run for this review; the focused tests and static checks are reported in `IMPLEMENTATION.md` and their saved logs. Other providers, the resumed matrix, and final release verification remain pending.
