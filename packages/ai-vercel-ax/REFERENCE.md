# Vercel and Ax adapter reference

Audience: application developers registering provider models, and implementers connecting the Spine Agent runtime.

`VercelAx.model()` registers an OpenAI Responses generation backend with `VercelAx.capabilities.openAIResponses()`. `VercelDecision.model()` registers an OpenRouter Jev decision backend with `VercelDecision.capabilities.openRouterJev()`. Both factories accept a semantic `ModelRef`, trusted identity and authorization callbacks, and a connection callback that constructs a published Vercel provider model using the supplied operation-scoped `fetch`. The connection returns that model and the same credential-free identity that the runtime authorized. Registration and connection do not dispatch a model request.

The generation path uses Ax to render requests, correct invalid output within the model-request allowance, and continue after recorded tool proposals. Direct Vercel provider streams carry native descriptor-derived JSON schemas or prompt-and-validate instructions. The adapter preserves bounded raw output, ordered provider tool proposals, actual model identity when reported, token usage with absent counts distinct from zero, and safe failure categories. It journals each physical attempt before tool authorization or a second model request. A runtime denial ends with `TOOL_FAILED`; an unresolved tool write ends with `TOOL_OUTCOME_UNKNOWN`. Neither becomes a fabricated tool result.

The decision path uses the pinned non-generative OpenRouter Jev protocol with SDK retries disabled. It forwards declared probability and score precision to definitive runtime admission and records that precision in `DecisionResponse`, including explicit zero versus absence. It does not use Ax chat correction for decisions.

The adapter guards each provider fetch by the authorized route, existing attempt ticket, durable reservation barrier, deadline, cancellation, execution fence, materialized input-byte limit, and received output-byte limit. The guarded fetch counts response bytes after the platform fetch has decoded transfer and content encoding; the count includes protocol framing and error response bodies. It reads one platform chunk at a time, so a chunk that crosses the limit may already have arrived before it is discarded. Parsed model text and tool input have a separate retained-output bound. The Spine runtime supplies authenticated selection, durable journal and budget callbacks, definitive Proto/application validation, tool policy and intent handling, and recovery. Direct use of a factory outside that runtime does not provide those guarantees.

The optional MCP protocol factory uses the pinned Vercel MCP client with a bounded custom HTTP or stdio transport. A session negotiates and discovers allowlisted tools before advertisement; accepted descriptions and input schemas are recorded with their server/tool mapping in the prepared generation request. The adapter validates arguments against the discovered schema and requires a runtime-reserved tool-call ticket before a physical `tools/call`. Runtime policy still decides whether a call is authorized and whether its effect is read or write. Every setup and call message uses a runtime reservation, counts decoded response bytes including errors and crossing chunks, and awaits `finishMessage` before passing a response to the MCP client. HTTP uses the configured POST endpoint without redirects, automatic GET subscriptions, or transport retries. Stdio uses a configured executable without a shell and caps each JSON-RPC line before SDK parsing. Each setup response is limited to 64 KiB; discovery is limited to eight pages, 64 tools, 4 KiB descriptions and 16 KiB input schemas. Local argument JSON has a separate 16 KiB ceiling. Unsupported schema features and binary/resource results fail explicitly. The initial MCP result contract accepts text and structured JSON only. Credential-free session identity hashes the full configured HTTP URL or the stdio executable, argument array and working directory; it does not expose those raw values, headers, or environment. The runtime must persist authorization, reservations, intent and results for durable recovery; this factory alone does not provide those guarantees.

See the [MCP configuration example](../ai/REFERENCE.md#configure-an-mcp-lookup) for the public server registration, per-tool permission and capability allowlist.

The built-in capability descriptors identify the tested provider protocol, schema or decision-output mode, guarded-fetch revision, ticket cancellation/deadline behavior, and one-call-per-ticket retry contract. The factories reject incomplete or changed descriptors. A custom provider model must route its exact Responses or Decisions request through the supplied scoped `fetch`, honor the published model interface, and avoid separate SDK retries; the descriptor alone cannot verify a custom model's internal network behavior.

The credential-free protocol tests use the pinned `@ax-llm/ax@25.0.0`, `ai@7.0.128`, `@ai-sdk/openai@4.0.84`, and `@openrouter/ai-sdk-provider@3.1.0`. They exercise actual SDK request shapes against local fetch fixtures, correction and tool continuation, invalid and truncated output, usage, cancellation, byte limits, journal barriers, and no-retry decisions. Run `pnpm exec vitest run packages/ai-vercel-ax/test` from the repository root.

The published AI SDK and Ax declarations produce errors under TypeScript 6 with `exactOptionalPropertyTypes`. This optional adapter's source-and-test tooling compilation and the single private BlackBox test that imports the OpenAI provider use `skipLibCheck: true` for vendor declarations; authored code keeps the repository's other strict checks. The general framework tooling compilation keeps `skipLibCheck: false`. The public model boundary uses direct `@ai-sdk/provider` V3/V4 interfaces, whose separate strict type fixture compiles with `skipLibCheck: false`.
